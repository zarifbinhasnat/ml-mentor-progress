# Day 62 — Causal Masking

## 🧠 CONCEPT OF THE DAY

**Intuition first.** Day 61 told you *that* decoder self-attention is causally masked. Today is *how* — and the "how" is not "delete the future," it's "redact it before anyone reads it." Think of the score matrix as a stack of sealed envelopes, one per (query, key) pair. A bad redaction opens every envelope, reads it, decides which answers to ignore, and only then reports back — the information was already seen. A good redaction stamps the disallowed envelopes with a value so extreme that opening them can never change the outcome, *before* the "read and combine" step (softmax) ever runs. That's the difference between an additive mask applied to raw scores and any scheme that tries to fix things up after the fact.

**The math.** Recall scaled dot-product attention from Day 55:

$$\text{Attn}(Q,K,V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}} + M\right)V$$

The mask $M$ is additive and applied **before** the softmax, with

$$M_{ij} = \begin{cases} 0 & j \le i \\ -\infty & j > i \end{cases}$$

Why additive, and why $-\infty$ specifically? Because softmax is $\text{softmax}(s)_j = e^{s_j} / \sum_k e^{s_k}$, and $e^{-\infty} = 0$. Adding $-\infty$ to a blocked score guarantees its post-softmax weight is *exactly* zero, not "very small" — no matter what the raw dot product $Q_i \cdot K_j$ happened to be. Compare that to the tempting-but-wrong alternative: compute the full softmax over all $n$ positions, then zero out the blocked entries afterward. That output is no longer a valid probability distribution (it doesn't sum to 1) unless you renormalize — and once you renormalize, you've just reinvented masked softmax the slow way, after paying the cost of computing exponentials for positions you were always going to throw away.

The additive form has a second, more important property: **masks compose by addition.** In real transformers you almost never have *only* a causal mask — you also have a padding mask (real tokens vs. pad tokens in a batch), and sometimes a sliding-window mask. Because $-\infty + \text{anything} = -\infty$ and $0 + 0 = 0$, you can precompute $M_{\text{causal}}$ and $M_{\text{padding}}$ independently and just sum them: $M = M_{\text{causal}} + M_{\text{padding}}$, then run one softmax. This is why the mask is implemented as a matrix added to scores rather than as, say, zeroing rows of $K$ or $V$ directly — masking $K$/$V$ doesn't compose the same way, and (as the interview question below gets at) doesn't even correctly block attention in the first place.

**Why it matters / where it leads.** This additive, precompute-once structure is exactly what makes causal masking cheap to fuse into a single kernel — you never materialize an intermediate "full" attention matrix and edit it. That fusion story is also the seed of Day 63 (the $O(n^2)$ memory/compute cost of the *full* $n \times n$ score matrix, mask or no mask) and Day 64 (FlashAttention, which exploits the causal mask's *structure* to skip computing blocked blocks entirely rather than computing-then-discarding them).

**Interview-style question:** *A colleague implements causal masking by zeroing the Value vectors $V_j$ for all future positions $j > i$, instead of adding $-\infty$ to the attention scores before softmax. Why is this wrong, and what would you observe in the trained model?* (Answer at the very bottom.)

## 🐍 PYTHONIC EDGE

Day 61 covered building the mask itself (`torch.triu` + `masked_fill`). The part that trips people up next is *reusing* it correctly — across batch, across heads, and across forward calls — without wasting memory or recomputing it every step.

```python
import torch
import torch.nn as nn

# ---------- the "bad" way: rebuild + manually tile the mask every forward() call ----------
class CausalAttnNaive(nn.Module):
    def __init__(self, seq_len, num_heads):
        super().__init__()                      # parent constructor call; C++ uses an initializer-list, Python calls it explicitly
        self.seq_len = seq_len
        self.num_heads = num_heads

    def forward(self, scores):                  # scores: (batch, heads, seq, seq)
        batch = scores.shape[0]
        mask = torch.triu(torch.ones(self.seq_len, self.seq_len), diagonal=1) * float("-inf")
        mask = torch.nan_to_num(mask, neginf=float("-inf"))
        # .repeat() ALLOCATES a full (batch, heads, seq, seq) copy of the mask every single call --
        # rebuilt from scratch, on every forward pass, for every batch.
        mask = mask.repeat(batch, self.num_heads, 1, 1)
        return torch.softmax(scores + mask, dim=-1)   # dim=-1: last axis, regardless of tensor rank

# ---------- the clean way: build once, register as a buffer, broadcast (no copy) at call time ----------
class CausalAttn(nn.Module):                     # class X(Base): single inheritance; C++: class X : public Base
    def __init__(self, max_seq_len):
        super().__init__()
        mask = torch.triu(torch.ones(max_seq_len, max_seq_len), diagonal=1).bool()
        # register_buffer: not a learnable Parameter, but still moves with .to(device)/.cuda()
        # and gets saved in state_dict() -- the right home for fixed, non-trainable tensors.
        self.register_buffer("causal_mask", mask)   # instance attribute set via self.x = ...; here via the buffer API

    def forward(self, scores):                  # __call__(scores) is what actually runs (hooks etc.); it invokes forward() for you -- never call .forward() directly
        seq_len = scores.shape[-1]
        # Slice to the ACTUAL sequence length -- max_seq_len was just an upper bound at init time.
        mask = self.causal_mask[:seq_len, :seq_len]      # slice notation [a:b], reused unchanged across every call
        # No .repeat(): broadcasting rules stretch a (seq, seq) mask against a (batch, heads, seq, seq)
        # tensor with ZERO extra memory allocated -- shapes just need to align from the right.
        scores = scores.masked_fill(mask, float("-inf"))
        return torch.softmax(scores, dim=-1)

attn = CausalAttn(max_seq_len=128)
fake_scores = torch.randn(2, 4, 10, 10)          # batch=2, heads=4, seq=10 -- mask (10,10) broadcasts against all of it
weights = attn(fake_scores)
```

The naive version pays two costs every call: building `torch.triu` from scratch (cheap but pointless if `seq_len` is fixed), and `.repeat()`, which actually materializes `batch * heads` copies of an `(seq, seq)` tensor in memory. The clean version builds the mask **once**, at `__init__` time, stores it as a `register_buffer` (so `model.to("cuda")` moves it along with the rest of the module's tensors — a `Parameter` would additionally get gradients, which a fixed mask should never receive), and leans on PyTorch's broadcasting to apply it against any batch/head shape with no copy at all.

## 📡 SIGNAL LAB

Day 61 connected causal masking to causal *filtering* (group delay, `filtfilt`). There's a sharper, more structural connection worth making today, specifically because it's the reason your DFT/FFT toolbox doesn't just "solve" causal attention for free.

A **circulant matrix** — the matrix form of *circular* convolution — is diagonalized by the DFT: its eigenvectors are exactly the Fourier basis vectors, and its eigenvalues are the DFT of its first column. That's the entire reason FFT-based convolution works: diagonalizing a matrix turns matrix-vector multiplication into elementwise multiplication in the transformed basis, $O(n \log n)$ instead of $O(n^2)$.

The causal mask, though, is a **lower-triangular Toeplitz matrix** (constant along diagonals, but only the lower triangle is nonzero) — the matrix form of *causal, non-circular* convolution. Triangular matrices are **not** circulant (a circulant matrix is fully determined by wraparound structure; a triangular one has none), so they are *not* diagonalized by the DFT. Concretely: for a $4\times 4$ circulant matrix built from first column $[h_0, h_1, h_2, h_3]$, every row is a cyclic shift of the previous one, and its eigenvalues are $\hat h_k = \sum_n h_n e^{-2\pi i kn/4}$ — pure FFT. For a $4\times4$ **causal** (lower-triangular) version of the same filter, row $i$ only has $i{+}1$ nonzero entries and there's no cyclic shift structure at all; its eigenvalues are just its diagonal entries (all equal to $h_0$ here), which tells you almost nothing useful about the filter's frequency response.

**So what:** this is exactly why fast causal attention (Day 64, FlashAttention) is an *I/O and memory-hierarchy* trick, not a Fourier trick — you cannot diagonalize your way out of the causal constraint the way you can for circular convolution. It also generalizes a lesson you already live with in frequency-domain image work: your fast, elegant DFT-domain filtering tricks (circular padding, FFT convolution theorem) all quietly assume circularity, and the instant you impose a genuinely causal or otherwise triangular structure — same as decoder self-attention — you fall back to $O(n^2)$ direct computation or accept an approximation (block processing, overlap-save with padding) that reintroduces some of what circularity gave you for free.

## 🏋️ THE GAUNTLET

**Problem: Cumulative Causal Bias**

You maintain a bias array over `n` positions, all initialized to `0`. You receive `q` operations **online, in order** (you must process each fully before seeing the next — no reordering, no batching ahead of time):

- `1 l r v` — add `v` to every position in `[l, r]` (inclusive).
- `2 i` — report the current bias value at position `i`.

Constraints: `1 <= n, q <= 2×10^5`, `0 <= l <= r < n`, `0 <= i < n`, `|v| <= 10^9`. Values can go negative; the running bias at any position fits in a 64-bit integer.

**Target:** `O((n + q) log n)` total — every operation in `O(log n)`.

**Pattern:** Fenwick tree (Binary Indexed Tree) over a **difference array** — range-update, point-query.

**Hints (escalating):**
1. A naive `add v to [l, r]` by looping over every index is `O(r - l)` per update — too slow if a single update spans most of the array and there are `2×10^5` of them. What if, instead of tracking the *value* at each position, you tracked how the value *changes* at just two boundary points?
2. If `diff[i] = bias[i] - bias[i-1]`, then `bias[i] = sum(diff[0..i])` — a prefix sum. Adding `v` to `bias[l..r]` corresponds to exactly **two** point updates on `diff`: `diff[l] += v` and `diff[r+1] -= v` (if `r+1 < n`). A Fenwick tree gives you `O(log n)` point-update **and** `O(log n)` prefix-sum, which is exactly the two operations you need on `diff`.
3. Build the Fenwick tree over `diff`, all zeros initially. For `1 l r v`: `update(l, +v)`, and if `r+1 < n`, `update(r+1, -v)`. For `2 i`: answer is `prefixSum(i)`. Watch the 1-indexing inside the Fenwick tree itself (BIT indices conventionally start at 1) versus the 0-indexed problem positions — an off-by-one here is the single most common bug in this pattern.

Full solution is under 🔓 GAUNTLET SOLUTION at the very bottom — try it for real before looking.

## 🏗️ BLUEPRINT

**Causal masking isn't just a training-time correctness requirement — it's the precondition that makes KV caching (Day 100 preview) valid at all.** Because $M_{ij} = -\infty$ for every $j > i$, token $i$'s attention output can *never* depend on any key/value computed for a token that comes after it. That means $K_j$ and $V_j$, once computed at the step where token $j$ was generated, are **frozen** for the rest of generation — no future token's arrival ever forces you to recompute them. That invariant is exactly what lets inference servers cache $K_j, V_j$ per layer and simply append new entries as generation proceeds, turning each decode step's attention cost from "recompute against everything" into "attend against a growing cache." The tradeoff you're prepaying for here: that cache grows linearly in sequence length ($O(n \cdot d_{\text{model}} \cdot \text{layers})$ memory), which is precisely the long-context memory pressure that windowed/sparse attention variants and paged KV-cache allocators (vLLM, Day 103) exist to manage. Bidirectional (encoder-style) attention has no equivalent cache, because a new token entering the sequence can change *every* existing token's attention output — there's nothing safe to freeze.

## 🗺️ MARCHING ORDERS

You now know not just *that* the future gets blocked, but *why* it's blocked additively, pre-softmax, and why that specific choice is what makes masks composable and caching valid. Tomorrow: Concept 63 — O(n²) cost & long-context pain.

## 🔓 GAUNTLET SOLUTION

```cpp
#include <bits/stdc++.h>
using namespace std;

struct Fenwick {
    int n;
    vector<long long> tree;
    Fenwick(int n) : n(n), tree(n + 1, 0) {}

    void update(int i, long long delta) {   // i is 0-indexed position; internally shifted to 1-indexed BIT
        for (int x = i + 1; x <= n; x += x & (-x)) {
            tree[x] += delta;
        }
    }

    long long prefixSum(int i) {             // sum of diff[0..i], i is 0-indexed
        long long sum = 0;
        for (int x = i + 1; x > 0; x -= x & (-x)) {
            sum += tree[x];
        }
        return sum;
    }
};

int main() {
    int n, q;
    cin >> n >> q;
    Fenwick fw(n);   // Fenwick tree built directly over the difference array (never materialized explicitly)

    while (q--) {
        int type;
        cin >> type;
        if (type == 1) {
            int l, r;
            long long v;
            cin >> l >> r >> v;
            fw.update(l, v);             // diff[l] += v
            if (r + 1 < n) fw.update(r + 1, -v);   // diff[r+1] -= v, only if r+1 is in range
        } else {
            int i;
            cin >> i;
            cout << fw.prefixSum(i) << "\n";   // bias[i] = prefix sum of diff[0..i]
        }
    }
    return 0;
}
```

Complexity: each `update` and `prefixSum` call touches `O(log n)` Fenwick nodes (the `x & (-x)` trick walks up/down the implicit tree via the lowest set bit), so all `q` operations run in `O(q log n)` total, `O(n)` space. The key insight the difference array buys you: a range update becomes exactly two point updates, at the cost of only being able to read back individual positions via a prefix sum rather than reading the range directly — which is precisely what the `2 i` query needs anyway.

## 💡 CONCEPT ANSWER

Zeroing $V_j$ for future positions doesn't stop the model from *attending* to them — it only stops their contribution to the weighted sum from mattering, after the attention weight has already been computed. The attention weight itself comes from $\text{softmax}(QK^\top/\sqrt{d_k})$, and $K_j$ for future positions is **not** zeroed in this scheme, so $Q_i \cdot K_j$ still produces some ordinary, non-$-\infty$ score. Softmax will happily assign real, nonzero probability mass to that future position based on it — mass that gets "spent" on a zero vector instead of being redistributed among the valid past positions. Two concrete symptoms follow: (1) the softmax denominator is inflated by $e^{\text{score}_j}$ terms for blocked positions that contribute nothing useful to the output, which *shrinks* the effective weight on real, valid context relative to properly-masked attention — the model gets systematically less signal from the tokens it's actually allowed to use; (2) at inference time, future positions don't exist yet at all — there's no $V_j$ to zero — so a model trained this way saw a subtly different attention-weight distribution during training (spread partly across "attend to nothing") than what it faces during autoregressive generation (nothing to spread across at all), a train/inference mismatch that degrades output quality in a way that, like Day 61's version of this bug, won't show up as an obviously bad training loss.
