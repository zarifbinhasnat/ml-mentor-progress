# Day 89 — Concept 89: Vision Transformer (ViT)

## 🧠 CONCEPT OF THE DAY

**Intuition.** Every CNN you've studied since Phase 4 builds understanding of an image bottom-up: a 3×3 kernel sees a tiny neighborhood, and only after many stacked layers does a unit's receptive field (Day 36) grow large enough to "see" the whole image — global context is *earned* through depth. The Vision Transformer throws that whole strategy out. Instead of sliding a small kernel across the image, it cuts the image into a grid of fixed-size, non-overlapping patches, flattens each patch into a vector, and treats the sequence of patch vectors exactly like a sequence of word tokens (Day 65). Once those "patch tokens" go through a standard Transformer encoder (Day 60), every patch can attend to every other patch **from layer one** — global receptive field on day one, no stacking required, at the cost of every one of the useful assumptions convolution baked in for free: locality, weight sharing, translation equivariance. ViT has to learn those regularities from data instead of getting them as architectural priors — which is the whole story of what makes it powerful and what makes it fragile.

**The math.** Given image $x \in \mathbb{R}^{H\times W\times C}$ and patch size $P$, reshape into $N = \frac{HW}{P^2}$ flattened patches $x_p^i \in \mathbb{R}^{P^2 C}$. A learned linear projection $E \in \mathbb{R}^{(P^2C)\times D}$ maps each patch to a $D$-dim token embedding; a learnable **class token** $x_{\text{class}}$ is prepended (the same trick BERT's `[CLS]` uses, Day 67), and learned position embeddings $E_{\text{pos}}$ are added since attention itself is permutation-invariant and has no sense of where a patch physically sat:

$$z_0 = [x_{\text{class}};\ x_p^1 E;\ x_p^2 E;\ \dots;\ x_p^N E] + E_{\text{pos}}$$

This sequence then passes through $L$ standard pre-norm Transformer encoder blocks (Day 60's residual + LayerNorm + multi-head self-attention + MLP recipe, unchanged):

$$z_\ell' = \text{MSA}(\text{LN}(z_{\ell-1})) + z_{\ell-1}, \qquad z_\ell = \text{MLP}(\text{LN}(z_\ell')) + z_\ell'$$

and the final class-token representation $y = \text{LN}(z_L^0)$ feeds a classification head. Notice there is no convolution anywhere in this stack — patch embedding is the *only* place spatial structure enters the model at all, and after that single linear projection, attention treats the image as an unordered bag of tokens that position embeddings alone have to keep straight.

**Why it matters / where it leads.** Dosovitskiy et al. (2020) found the tradeoff is brutal in one direction and generous in the other: trained from scratch on mid-sized datasets, ViT *underperforms* a same-size ResNet, because it's missing the locality/equivariance priors CNNs get for free and has to rediscover them purely from data. But pretrained on hundreds of millions of images, ViT matches or beats CNNs outright — with enough data, learning the inductive bias beats hard-coding it. This is precisely the "data-hungry transformer vs. sample-efficient CNN" tradeoff a senior interviewer will push you on, and it's also the direct setup for the rest of this phase: tomorrow's CLIP pairs a ViT image encoder with a text encoder via contrastive learning, and everything from 91 (SimCLR) through 95 (detection) builds on "patches as tokens" as the new default vision primitive.

**Interview question:** *You have a labeled dataset of only 50,000 images. Would you expect a ViT-Base trained from scratch to outperform or underperform a ResNet-50 of comparable parameter count, and why? Name one practical fix that lets you use ViT anyway on a dataset this small.*

## 🐍 PYTHONIC EDGE

Patch embedding is "reshape image into non-overlapping blocks, then linearly project each block" — the naive version crops patches with a Python double loop; the version everyone actually ships is a single strided convolution, because a `Conv2d` with `kernel_size = stride = patch_size` computes exactly the same "flatten patch, multiply by learned weight matrix" operation as a fused, hardware-optimized op.

```python
import torch
import torch.nn as nn

# ---- BAD: manually crop each patch in nested Python loops, then apply a Linear ----
def patchify_bad(img, patch_size, proj_weight):    # img: (C, H, W) tensor
    C, H, W = img.shape
    patches = []
    for y in range(0, H, patch_size):               # range() with a step arg -- lazy iterator, not a materialized list
        for x in range(0, W, patch_size):
            patch = img[:, y:y+patch_size, x:x+patch_size]   # slice notation [a:b] -- half-open, no bounds-check exception like .at()
            patches.append(patch.flatten() @ proj_weight)    # @ is matrix multiplication (not bitwise-AND, unlike C++'s &)
    return torch.stack(patches)                      # O(H*W/P^2) Python-level iterations, one CPU->kernel-launch per patch

# ---- CLEAN: a single strided conv does patch-crop + flatten + linear-project in one fused op ----
class PatchEmbed(nn.Module):                          # class X(Base): single inheritance; C++ would write class X : public Base
    def __init__(self, patch_size=16, in_channels=3, embed_dim=768):
        super().__init__()                            # runs Base.__init__ first; C++ uses an initializer-list instead
        self.proj = nn.Conv2d(                         # instance attribute set via self.x = ...; C++ declares in the header, inits in the body
            in_channels, embed_dim,
            kernel_size=patch_size, stride=patch_size,  # kernel == stride -> non-overlapping tiles, no padding needed
        )

    def forward(self, x):                              # x: (B, C, H, W); note the batch dim -- torch never drops it implicitly
        x = self.proj(x)                                # -> (B, embed_dim, H/P, W/P): one D-dim vector per patch, already projected
        return x.flatten(2).transpose(1, 2)             # flatten(2) merges dims from index 2 onward; .transpose swaps two dims (not a full permute)

patch_embed = PatchEmbed()
img_batch = torch.randn(8, 3, 224, 224)
tokens = patch_embed(img_batch)                         # calls __call__, which wraps forward() with hooks -- never call .forward() directly
```

Both compute the identical mathematical operation — `Conv2d(kernel=stride=P)` *is* "slice into non-overlapping $P\times P$ blocks, flatten, matmul by a shared weight" — but the clean version is one cuDNN kernel launch instead of thousands of tiny slice-and-matmul ops, which is why every real ViT implementation (including the original) builds patch embedding out of a single conv layer rather than an explicit crop loop.

Left: a 1D toy signal (a smooth low-frequency edge plus mid- and near-Nyquist high-frequency texture, seeded) overlaid with its patch=16 box-average reconstruction, which reduces to a staircase that tracks the edge but erases the fine texture within each patch. Center: the frequency response |H(f)| of a box-average (patchify) filter for patch sizes 8, 16, and 32 -- each is a sinc-shaped low-pass with its first null at 1/P, so larger patches null out lower frequencies and act as a more aggressive low-pass. Right: FFT magnitude of the original signal versus the patch-16 and patch-32 reconstructions -- the low/mid-frequency peak near 0.12 cycles/pixel survives reasonably well in both, but the high-frequency peak near 0.40 cycles/pixel (matching the injected near-Nyquist texture) is almost entirely gone in the reconstructions.](graph_DAY_89.png)

**Worked insight.** Strip away the learned weights and a patch embedding's spatial-averaging character is just a boxcar filter of width $P$ applied to the image, then downsampled to one value per patch — exactly what `patchify_boxcar` computes in the script. A boxcar's frequency response is a sinc, with its first null at $f = 1/P$: patch size $P{=}32$ nulls out frequencies almost 3× lower than $P{=}8$ does, meaning **the patch-size hyperparameter is literally an anti-aliasing cutoff you're choosing before the transformer ever sees a pixel.** The right panel confirms it end-to-end — the near-Nyquist texture component the toy signal was built with is essentially invisible in either patch reconstruction, while the coarser edge structure survives.

**So what.** This has a direct, underappreciated consequence for your research lane. A CNN-based deepfake/generative-artifact detector operates on raw pixel-resolution feature maps and can, in principle, pick up the exact high-frequency periodic replication signatures from Day 88. A ViT-based detector (and any CLIP- or DINO-backed forensic classifier built on top of one) has already thrown away frequency content above roughly $1/(2P)$ at the very first layer, purely as a side effect of tokenization — before a single attention weight has been learned. That's a real, testable hypothesis, not hand-waving: if you ever benchmark a ViT-based vs. CNN-based forgery detector and find the ViT one is selectively blind to a particular class of high-frequency spectral artifact, patch-size-induced anti-aliasing is the first place to look, and finer patch sizes (or patch overlap) are the first knob to try.

## 🏋️ THE GAUNTLET

**Subarray Sum Equals K.** Given an integer array `nums` and an integer `k`, return the total number of contiguous subarrays whose elements sum to exactly `k`. Elements can be negative.

**Constraints:**
- `1 <= nums.length <= 2 * 10^4`
- `-1000 <= nums[i] <= 1000`
- `-10^7 <= k <= 10^7`

**Hints (escalating):**
1. The brute-force approach checks every pair of start/end indices — that's every one of the $O(n^2)$ subarrays, mirroring the "every patch attends to every other patch" cost you just met in ViT. Before reaching for that, ask: can you avoid recomputing a subarray sum from scratch for every pair?
2. Define $P[i] = \sum_{j \le i} \text{nums}[j]$, the prefix sum up to index $i$. The sum of any subarray $(i, j]$ is just $P[j] - P[i]$ — a single subtraction, not a re-scan. So "does a subarray ending at $j$ sum to $k$" becomes "does some earlier prefix sum equal $P[j] - k$?"
3. That's a membership + count query against *all prior prefix sums at once* — exactly the shape a hashmap answers in $O(1)$ average. Walk the array once maintaining a running prefix sum and a hashmap of `prefix_sum -> count of times seen so far` (seeded with `{0: 1}` for the empty prefix), and at each index add `map[running_sum - k]` to your answer before recording the current running sum.

**Pattern:** prefix sum + hashmap frequency count — turning an $O(n^2)$ all-pairs scan into a single $O(n)$ pass, the same trick that makes a hashmap lookup a drop-in replacement for an expensive pairwise comparison whenever you can rephrase "does some earlier state satisfy X" as an equality test. **Target complexity:** $O(n)$ time, $O(n)$ space.

## 🏗️ BLUEPRINT

**Patch size is a compute-vs-fidelity knob at serving time, and it interacts with attention's quadratic cost non-linearly.** Halving patch size at fixed image resolution doubles the tokens per side, so the *total* token count $N$ quadruples — and attention cost scales as $O(N^2)$, so that's a **16×** jump in attention FLOPs for the same image. A CNN's compute, by contrast, scales close to linearly in pixel count, because convolution stays local regardless of resolution. This is exactly why serving ViT at high resolution (medical scans, satellite tiles, forensic image analysis at full sensor resolution) hits a much steeper latency cliff than serving a same-resolution CNN, and it's the direct motivation for windowed/hierarchical attention variants like Swin Transformer — and for why production ViT deployments default to a deliberately coarse patch size (14–32px) rather than the finer patches that would, per today's signal lab, preserve more high-frequency detail.

## 🔓 GAUNTLET SOLUTION

```cpp
#include <bits/stdc++.h>
using namespace std;

int subarraySum(vector<int>& nums, int k) {
    unordered_map<long long, int> prefixCount;
    prefixCount[0] = 1;              // empty prefix, sum 0, seen once

    long long running = 0;
    int answer = 0;
    for (int x : nums) {
        running += x;
        auto it = prefixCount.find(running - k);
        if (it != prefixCount.end()) answer += it->second;
        prefixCount[running]++;
    }
    return answer;
}
```

One pass over `nums`, one hashmap lookup and one hashmap increment per element — both $O(1)$ average — for $O(n)$ time and $O(n)$ space in the worst case (all prefix sums distinct). Using `long long` for the running sum and map keys avoids overflow given the stated constraints.

## 💡 CONCEPT ANSWER

Expect ViT-Base to **underperform** ResNet-50 from scratch on only 50k labeled images. ResNet's convolutional layers bake in locality and translation equivariance as hard architectural priors — the network starts already "knowing" that nearby pixels are related and that a learned pattern should fire the same way regardless of where it appears in the image — so it needs comparatively little data to find good filters. ViT has no such prior: it has to *learn from examples alone* that nearby patches matter more than distant ones and that patterns should be treated consistently across positions, and 50k images is nowhere near enough for pure attention plus an MLP to discover that structure reliably; the original paper shows this gap directly on ImageNet-scale (~1M image) training, and it only gets worse at 50k. The practical fix is exactly what the paper's results imply: don't train ViT from scratch on a small dataset — start from a checkpoint pretrained on a large corpus (ImageNet-21k, LAION, etc.) and fine-tune on your 50k images, so the model only has to adapt already-learned general visual structure to your task rather than discover locality and translation-equivariance-like regularities from a small sample. A softer middle-ground fix, if pretrained weights genuinely aren't available, is a hybrid architecture that keeps a shallow convolutional stem before the transformer blocks, reintroducing some locality bias by construction instead of relying on data alone to find it.
