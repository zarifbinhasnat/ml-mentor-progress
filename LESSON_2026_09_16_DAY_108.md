# Day 108 — Concept 108: RAG (Retrieval-Augmented Generation)

## 🧠 CONCEPT OF THE DAY

**Intuition.** A closed-book exam forces you to answer from memory alone — and an LLM's weights are exactly that: a fixed, frozen memory baked in at training time. RAG turns it into an *open-book* exam: before the model writes an answer, it's handed the most relevant pages pulled from an external library, and it's allowed to read them first. The model still does the reasoning and writing, but it no longer has to have memorized every fact — it just has to know how to *use* what it's given.

This matters because model weights are expensive to update and go stale the moment training ends. A vector database of documents can be updated in seconds. RAG decouples "what the model knows" from "what the model was trained on."

**The mechanics.** Two stages, bolted together:

1. **Retriever** — embed the query and every candidate document into the same vector space, then rank documents by similarity to the query.

Similarity is almost always cosine similarity between query embedding $q$ and document embedding $d$:

$$\text{sim}(q, d) = \frac{q \cdot d}{\lVert q \rVert \, \lVert d \rVert}$$

Take the top-$k$ documents by this score — this is nearest-neighbor search over an index (exact, or approximate via HNSW/IVF at scale).

2. **Generator** — concatenate the retrieved documents $D = \{d_1, \dots, d_k\}$ with the original query into an augmented prompt, and let the LLM produce the answer conditioned on both:

$$P(y \mid q, D) = P(y \mid q, d_1, \dots, d_k)$$

That's it — no gradient ever flows through the retrieval step in the basic (non fine-tuned) setup; it's pure inference-time lookup feeding a normal causal LM forward pass. This is also *why* it composes so cleanly with everything you already know: the retriever is just embeddings (Concept 66) plus a similarity score, and the generator is a plain decoder doing next-token prediction (Concept 68) over a longer context window.

**Why it matters / where it leads.** RAG is the simplest possible instance of "give the model access to something outside its own weights at inference time" — which is precisely what Concept 109 (Agents & tool use) generalizes: instead of *always* retrieving from a fixed vector store, an agent *decides* whether to call a retriever, a calculator, a search API, or nothing at all. RAG is a one-tool, no-decision agent.

**Interview-style question:** Your RAG system retrieves documents that are topically relevant to the query but factually contradict each other (e.g., two versions of a policy doc, one outdated). The generator confidently picks one and states it as fact. How would you redesign the pipeline to reduce this failure mode?

## 🐍 PYTHONIC EDGE

Computing cosine similarity between one query and many documents is a classic "don't loop, broadcast" moment.

```python
import numpy as np

# ---- the bad way: explicit Python loop ----
def cosine_sim_loop(query, docs):
    sims = []
    for d in docs:                      # `in` here is membership/iteration, not C++ range-for's reference binding
        num = np.dot(query, d)          # @ or np.dot both do matmul/dot product — no operator overload needed like C++'s operator*
        denom = np.linalg.norm(query) * np.linalg.norm(d)
        sims.append(num / denom)        # list.append, not push_back
    return sims                         # returns a plain list, not a numpy array — easy bug source

# ---- the clean way: vectorized broadcast ----
def cosine_sim_batch(query, docs):
    q_norm = query / np.linalg.norm(query)                 # / is true division; no need for casting like C++ ints
    d_norms = docs / np.linalg.norm(docs, axis=1, keepdims=True)  # axis=1: reduce across columns, one norm per row
    return d_norms @ q_norm                 # @ is matmul: (n_docs, dim) @ (dim,) -> (n_docs,) in one C call, no Python loop
```

`cosine_sim_loop` pays Python interpreter overhead per document — fine for 10 docs, ruinous for 10M. `cosine_sim_batch` pushes the whole reduction into compiled numpy code via broadcasting (`keepdims=True` keeps the norm's shape `(n_docs, 1)` so it divides elementwise against `(n_docs, dim)` instead of raising a shape-mismatch error — there's no implicit broadcasting rule in C++ to fall back on, so this is a distinctly NumPy idiom). Rule of thumb: if you're writing `for x in array:` to compute a per-element numeric result, there's almost always a broadcast or reduction that replaces it.

## 📡 SIGNAL LAB

Cosine-similarity retrieval and **matched filtering** are the same idea wearing different clothes. In DSP, when you want to detect where a known template signal $s[n]$ occurs inside a noisy observation $x[n]$, you correlate:

$$r[k] = \sum_n x[n+k] \, s[n]$$

and the location of the peak of $r[k]$ tells you where the template best matches — that peak-finding *is* nearest-neighbor retrieval, just in the shift domain instead of an embedding space. Normalizing $r[k]$ by the local energy of $x$ turns raw correlation into *normalized* cross-correlation, which is exactly cosine similarity applied window-by-window.

**Worked example.** Detect a short chirp template hidden in noise using FFT-based cross-correlation (fast, avoids the O(N·M) direct-convolution cost):

```python
import numpy as np

np.random.seed(42)
N = 500
n = np.arange(N)

# Template: a short chirp "signature"
t = np.arange(40)
template = np.sin(2 * np.pi * (0.02 * t + 0.001 * t**2))

# Observation: noise, with the template embedded at a hidden offset
signal = 0.6 * np.random.randn(N)
true_offset = 220
signal[true_offset:true_offset + len(template)] += template

# Cross-correlation via FFT (fast path — O(N log N) instead of O(N*M))
fft_len = N + len(template) - 1
S = np.fft.rfft(signal, n=fft_len)
T = np.fft.rfft(template[::-1], n=fft_len)   # reversed template = correlation, not convolution
corr = np.fft.irfft(S * T, n=fft_len)

# Normalize by local energy so amplitude doesn't fake out the peak (-> cosine similarity, not raw dot product)
local_energy = np.sqrt(np.convolve(signal**2, np.ones(len(template)), mode="full")) + 1e-8
norm_corr = corr / local_energy
detected_offset = np.argmax(norm_corr) - (len(template) - 1)

print(f"true offset: {true_offset}, detected offset: {detected_offset}")
```

**So what:** a RAG vector index doing approximate nearest-neighbor search over millions of embeddings is functionally the same operation as this correlator sweeping over the whole signal, just in a high-dimensional semantic space instead of a 1-D time axis — and both get their speedup from the same trick: FFT turns O(N·M) direct correlation into O(N log N), the way ANN indices (HNSW/IVF) turn O(N·k) brute-force cosine search into sublinear lookup. If you ever end up doing retrieval over spectrograms or frequency-domain features (very much your lane), the "similarity search" and "matched filter" framings are literally interchangeable.

## 🏋️ THE GAUNTLET

**Problem — K Closest Points to Origin** *(this is retrieval's core primitive: "give me the top-k nearest neighbors to a query point")*

Given an array of `n` points on the 2D plane and an integer `k`, return the `k` points closest to the origin `(0, 0)`, in any order. Distance is standard Euclidean distance.

**Constraints:** `1 <= k <= n <= 10^5`, coordinates fit in a 32-bit int.

**Hints (escalating):**
1. You don't need the actual sorted order of *all* points — you only need to identify the `k` smallest distances. What's the cost of a full sort, and can you avoid paying for the part you don't need?
2. Think about maintaining a running "worst of the best" — a data structure that lets you cheaply evict your current weakest candidate the moment a better one shows up, without re-scanning what you've already accepted.
3. There's also a `O(n)` expected-time approach that never fully sorts — it partitions the array around a pivot the way a certain sort algorithm's partition step does, recursing into only the half that matters.

**Pattern:** heap-based top-k selection (or quickselect for the optimal average case). **Target complexity:** `O(n log k)` with a heap, or `O(n)` expected with quickselect — both beat the naive `O(n log n)` full sort.

## 🏗️ BLUEPRINT

RAG is one of the few concepts where the *system design* is the concept. One key tradeoff to sit with: **ANN index choice trades recall for latency**, and it compounds with chunking. HNSW gives high recall and fast queries but costs more memory and slower inserts; IVF (inverted file index) is cheaper to build and update but needs more careful tuning of the number of probed clusters to hit the same recall. Whichever you pick, it's downstream of a decision made earlier and harder to fix later: chunk size. Chunk too large and irrelevant text dilutes the embedding and drowns your signal; chunk too small and you lose the surrounding context a retrieved snippet needs to be useful once it lands in the prompt.

🔓 GAUNTLET SOLUTION

```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    vector<vector<int>> kClosest(vector<vector<int>>& points, int k) {
        // Max-heap keyed on squared distance (avoid sqrt — monotonic transform, doesn't change ordering)
        auto cmp = [](const vector<int>& a, const vector<int>& b) {
            long long da = (long long)a[0]*a[0] + (long long)a[1]*a[1];
            long long db = (long long)b[0]*b[0] + (long long)b[1]*b[1];
            return da < db; // max-heap: largest distance at the top
        };
        priority_queue<vector<int>, vector<vector<int>>, decltype(cmp)> maxHeap(cmp);

        for (auto& p : points) {
            maxHeap.push(p);
            if ((int)maxHeap.size() > k) {
                maxHeap.pop(); // evict the current farthest point once we exceed k
            }
        }

        vector<vector<int>> result;
        result.reserve(k);
        while (!maxHeap.empty()) {
            result.push_back(maxHeap.top());
            maxHeap.pop();
        }
        return result; // O(n log k) time, O(k) extra space
    }
};
```

*Quickselect variant (O(n) expected): partition the array around a pivot by squared distance, as in the partition step of quicksort; if the pivot lands exactly at index `k`, the first `k` elements are your answer — otherwise recurse into only the side that contains index `k`. Average case discards half the remaining work at each step instead of paying for a full sort.*

💡 CONCEPT ANSWER

Treat contradictory or stale retrieved documents as a data-quality problem the pipeline must surface, not hide:

- **Re-rank before generation** with a cross-encoder that scores (query, doc) pairs jointly — cosine similarity from independent embeddings is a good recall filter but a weak precision signal when documents are near-duplicates with conflicting content.
- **Attach and surface metadata** (timestamp, source authority, version) and either filter by recency/authority at retrieval time or pass the metadata into the prompt so the generator can reason about which source to trust, rather than silently averaging them into one confident-sounding answer.
- **Force citations** — require the generator to attribute each claim to a specific retrieved chunk. This doesn't fix contradictions, but it makes them visible and auditable instead of silently resolved.
- **Confidence/abstention threshold** — if top retrieved documents disagree strongly or similarity scores are all mediocre, prefer "I don't have a reliable answer" over a fluent guess. A senior interviewer is listening for whether you treat hallucination as a *retrieval quality and prompting* problem, not just a "bigger model" problem.
