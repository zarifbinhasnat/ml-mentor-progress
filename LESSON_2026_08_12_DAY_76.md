# Day 76 — Mixture of Experts (MoE)

## 🧠 CONCEPT OF THE DAY

**Intuition.** A dense transformer FFN makes every token walk through the *same* set of weights. That's like sending every hospital patient through every specialist — thorough, but wildly wasteful. A Mixture of Experts replaces the single FFN with a bank of N smaller FFNs ("experts") plus a lightweight **router** (a triage nurse) that looks at each token and sends it to only the 1–2 experts most relevant to it. You get the *capacity* of a huge model (all N experts' parameters exist and get trained) while paying the *compute* of a small one (only k of them run per token).

This is the key decoupling that makes 2026-era frontier models tractable: **total parameters** (knowledge capacity) and **active parameters per token** (inference/training FLOPs) stop being the same number.

**The math.**

For a token with hidden state $x$, a router (a single linear layer) produces logits over $N$ experts:

$$g(x) = W_g x, \qquad p(x) = \text{softmax}(g(x))$$

where $W_g \in \mathbb{R}^{N \times d}$ and $p_i(x)$ is the router's affinity for expert $i$. We keep only the top-$k$ entries of $p(x)$ (renormalized among themselves) and zero out the rest — this sparsity is what makes it cheap:

$$y = \sum_{i \in \text{TopK}(p(x))} p_i(x) \cdot E_i(x)$$

Each $E_i$ is its own small FFN with independent weights. If $k \ll N$, forward cost per token is roughly $k/N$ of running a dense FFN of the same total parameter count.

Left unconstrained, the router degenerates: a few experts get slightly ahead early in training, receive more gradient signal, get better, and attract even more tokens — **expert collapse**. The fix is a **load-balancing auxiliary loss** (Shazeer et al. 2017, refined in Switch Transformer / GShard):

$$L_{\text{aux}} = N \cdot \sum_{i=1}^{N} f_i \cdot P_i$$

where $f_i$ is the fraction of tokens in the batch actually routed to expert $i$, and $P_i$ is the router's *average* softmax probability assigned to expert $i$ across the batch. This is minimized when both are uniform ($f_i = P_i = 1/N$), and it's differentiable through $P_i$ even though $f_i$ (a hard argmax/top-k count) isn't.

**Why it matters / where it leads.** MoE is *how* you push past dense scaling laws without a proportional compute bill — which is exactly tomorrow's topic (Concept 77: scaling laws, and the compute-optimal frontier). It's also the backbone of Mixtral, DeepSeek-MoE, and (reportedly) GPT-4-class models. The failure modes above are exactly what a senior interviewer will probe.

**Interview question:** *Why might an 8-expert, top-2 MoE model underperform a dense model with the same number of **active** parameters per token, and what specific router failure mode usually explains it?* (Answer at the bottom.)

## 🐍 PYTHONIC EDGE

Vectorizing top-k expert routing — the naive per-token Python loop vs. the batched `torch.topk` version.

```python
import torch  # no "using namespace" — everything is module-qualified, e.g. torch.topk

# ---------- BAD: Python-level loop over tokens ----------
def route_naive(logits):
    # logits: [num_tokens, num_experts]  (tensor shape ~ C++ std::vector<std::vector<float>>,
    # but a single contiguous buffer under the hood, not nested containers)
    topk_idx = []
    topk_val = []
    for row in logits:                       # iterating a 2D tensor yields 1D row tensors — like
                                               # iterating a matrix by reference to each row
        vals, idx = torch.topk(row, k=2)      # per-row Python-level call: N calls, N dispatch overheads
        topk_idx.append(idx)
        topk_val.append(vals)
    return torch.stack(topk_idx), torch.stack(topk_val)  # torch.stack ~ concatenating N small
                                                            # buffers into one; no C++ equivalent
                                                            # one-liner, you'd write the loop manually

# ---------- CLEAN: one vectorized call, GPU does all rows in parallel ----------
def route_batched(logits):
    # dim=-1 means "last axis" (negative indexing on axes, like logits[-1] on elements) —
    # here it says "take top-k along the expert dimension, independently per token row"
    vals, idx = torch.topk(logits, k=2, dim=-1)   # ** no ** here — topk isn't exponentiation,
                                                    # just showing where ** WOULD read differently
    weights = torch.softmax(vals, dim=-1)          # renormalize only among the chosen k
    return idx, weights

logits = torch.randn(4096, 8)   # 4096 tokens, 8 experts — one call, not 4096
idx, weights = route_batched(logits)
assert idx.shape == (4096, 2)   # assert is a runtime check, stripped under `python -O`
                                 # (C++ analog: assert() from <cassert>, also stripped by NDEBUG)
```

`route_naive` pays Python-interpreter + CUDA-launch overhead once *per token*; `route_batched` issues one kernel launch for the whole batch and lets the GPU parallelize the row-wise top-k internally. On real batch sizes this is a 100–1000x wall-clock difference, not a micro-optimization — this is precisely the kind of loop a MoE router must never contain.

## 📡 SIGNAL LAB

**Setup.** MoE routing has a clean DSP analogue: **subband decomposition**. Instead of one filter processing a whole signal, you split it into frequency bands and let a specialized filter handle each band — a low-pass "expert" for the slow-varying trend, a high-pass "expert" for fast detail. The "router" is just: *which band does this energy belong to?*

Build a synthetic signal = a slow sine (5 Hz) + a fast sine (60 Hz) + noise, sampled at 500 Hz (well above Nyquist for both components: $f_s/2 = 250\text{Hz} \gg 60\text{Hz}$).

```python
import numpy as np

np.random.seed(42)
fs = 500                                  # sampling rate (Hz)
t = np.arange(0, 1, 1 / fs)               # 1 second, 500 samples
x = np.sin(2 * np.pi * 5 * t) + 0.5 * np.sin(2 * np.pi * 60 * t) + 0.2 * np.random.randn(len(t))

X = np.fft.rfft(x)
freqs = np.fft.rfftfreq(len(t), d=1 / fs)

# "Router": assign each frequency bin to whichever expert band it falls in
low_expert_mask = freqs < 20                    # expert 1: trend/low-freq
high_expert_mask = ~low_expert_mask              # expert 2: detail/high-freq

X_low  = X * low_expert_mask
X_high = X * high_expert_mask

x_low  = np.fft.irfft(X_low,  n=len(t))          # expert 1's reconstruction
x_high = np.fft.irfft(X_high, n=len(t))          # expert 2's reconstruction
x_recon = x_low + x_high                         # combine — router weights here are hard 0/1

print(np.allclose(x_recon, x, atol=1e-10))       # True: hard-routed subbands losslessly recombine
```

**So what.** With a *hard*, non-overlapping mask this is a lossless partition — exactly analogous to a top-1 MoE router with disjoint, perfectly-specialized experts: no capacity is wasted, no information crosses bands. Real MoE routers are soft and imperfect (Gaussian-ish overlap between "which expert should this token go to"), which is precisely why $L_\text{aux}$ and top-$k>1$ exist — they're the ML equivalent of using overlapping/windowed subbands (like an STFT with overlapping windows) instead of a brick-wall filter bank, trading a bit of redundancy for robustness against a token/frequency sitting right on a boundary. Your forensics work on spectral signatures of generated images (Day 88 preview) leans on exactly this: generators leave energy imbalances across specific subbands that a naive full-spectrum classifier under-weights, the same way a collapsed router under-weights unpopular experts.

## 🏋️ THE GAUNTLET

**Token Dispatch Order**

You're given an array `experts` of length $n$, where `experts[i]` is the expert ID (an integer in `[0, m)`) that token $i$ has been routed to. Before physically dispatching tokens to GPU-resident expert buffers, you must **reorder** the sequence so that no two *adjacent* tokens in the dispatch order go to the same expert (back-to-back same-expert tokens serialize on that expert's buffer and stall the pipeline).

Return **any** valid reordering (as a permutation of the multiset of expert IDs), or an empty array if no valid ordering exists.

**Constraints:**
- $1 \le n \le 10^5$
- $0 \le \texttt{experts}[i] < m \le 10^4$
- Target complexity: $O(n \log m)$

**Hints:**
1. There's a simple necessary-and-sufficient feasibility condition before you even think about construction — relate the count of the *most frequent* expert to $n$.
2. A naive greedy that re-sorts by remaining frequency at every step is $O(n \cdot m)$. What data structure gives you "the currently most-frequent remaining expert" in $O(\log m)$ instead of $O(m)$?
3. You can't place the same expert twice in a row — but you also can't just skip it forever. Try holding the just-placed expert "in the penalty box" for exactly one slot before it's eligible again.

**Pattern:** Greedy + max-heap with a one-slot cooldown (same family as *Task Scheduler* / *Reorganize String*).
**Target:** $O(n \log m)$ time, $O(m)$ extra space.

## 🏗️ BLUEPRINT

**Expert parallelism, briefly.** In multi-GPU MoE training, experts are sharded one-or-few-per-GPU. Each GPU computes routing locally, then an **all-to-all** collective ships each token's activations to the GPU holding its chosen expert, and another all-to-all brings the results back. The tradeoff: FLOPs scale beautifully with more experts (each GPU still only runs its local expert on the tokens routed to it), but **network bandwidth for the all-to-all becomes the bottleneck**, not compute — past a certain expert count/cluster size, MoE stops being "free capacity" and starts being a communication-bound system. This is why capacity factor (a hard per-expert token cap, dropping overflow) exists: it bounds the worst-case all-to-all payload size, trading a little accuracy for predictable network cost.

🔓 GAUNTLET SOLUTION
```cpp
#include <vector>
#include <queue>
#include <unordered_map>
using namespace std;

vector<int> reorderExperts(vector<int>& experts) {
    int n = experts.size();
    unordered_map<int, int> freq;
    for (int e : experts) freq[e]++;

    // Feasibility: the most frequent expert can't need more "slots" than
    // available under a strict no-adjacent-repeat placement.
    int maxFreq = 0;
    for (auto& [expert, count] : freq) maxFreq = max(maxFreq, count);
    if (maxFreq > (n + 1) / 2) return {};   // impossible, e.g. [0,0,0] with only 1 other id

    // Max-heap keyed by remaining count, O(log m) to grab current max.
    priority_queue<pair<int, int>> pq;      // (count, expert_id)
    for (auto& [expert, count] : freq) pq.push({count, expert});

    vector<int> result;
    result.reserve(n);
    pair<int, int> cooldown = {0, -1};      // holds the just-placed (count-1, id) for one slot

    while (!pq.empty()) {
        auto [count, expert] = pq.top();
        pq.pop();

        result.push_back(expert);

        // Release whatever was in the penalty box last round, if it still has copies left.
        if (cooldown.first > 0) pq.push(cooldown);

        cooldown = {count - 1, expert};     // this expert can't be reused for one more slot
    }

    // The last item placed into "cooldown" never got a chance to be re-pushed and re-popped —
    // but by then all tokens are already placed, so result.size() == n confirms validity.
    return result.size() == (size_t)n ? result : vector<int>{};
}
```
The heap always emits the globally most-starved expert next, and the one-slot cooldown enforces the no-adjacent-repeat constraint without ever comparing against more than the single most recently placed element — giving $O(n \log m)$ overall.

💡 CONCEPT ANSWER
An 8-expert, top-2 MoE can underperform a dense model with matching *active* params when the router suffers **expert collapse**: without (or with too weak) a load-balancing auxiliary loss, the router's softmax quickly concentrates on a small winning subset of experts early in training (a rich-get-richer feedback loop — popular experts get more gradient signal, get better, get picked even more). Effectively only 2–3 of the 8 experts are ever well-trained; the rest see so few tokens they stay near-random. So although the *architecture* has 8 experts' worth of capacity, the *realized* capacity is much closer to a 2–3-expert model — while still paying the router's overhead and losing the specialization benefit that motivated using MoE in the first place. The fix is the $L_\text{aux}$ load-balancing loss (and/or noise injection into router logits, and a capacity factor that hard-caps and drops overflow tokens per expert) to keep $f_i$ and $P_i$ close to uniform.
