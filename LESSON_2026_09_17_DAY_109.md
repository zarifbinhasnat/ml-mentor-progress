# Day 109 — Concept 109: Agents & Tool Use

## 🧠 CONCEPT OF THE DAY

**Intuition.** RAG (yesterday) gave the model one fixed helper: always look something up in the same vector store, no matter the question. An **agent** upgrades that to a research assistant with a whole phone book of specialists — a calculator, a web search API, a code executor, a RAG retriever — who *decides*, question by question, whether to call anyone at all, who to call, what to ask them, and whether the answer they get back is enough to stop. The LLM stops being a single forward pass that emits an answer, and becomes the *controller* of a loop: think, act, observe, repeat.

**The mechanics.** The dominant pattern (ReAct: Reason + Act) turns generation into an interleaved loop of three token types:

$$\text{Thought}_t \to \text{Action}_t \to \text{Observation}_t \to \text{Thought}_{t+1} \to \cdots$$

At each step the model conditions on everything so far — the original query plus the full thought/action/observation history $H_t$ — and produces the next thought and action:

$$a_t \sim \pi_\theta(\cdot \mid q, H_t)$$

where $a_t$ is either a tool call (name + arguments) or a special `finish` action carrying the final answer. If $a_t$ is a tool call, the *environment* (not the model) executes it and returns an observation $o_t$, which gets appended to $H_t$ to form $H_{t+1}$. No weights update during this loop — it's pure inference-time control flow, exactly like RAG's retrieval step, just generalized to *any* external capability and *made a decision* instead of a fixed pipeline stage.

Notice the shape of this: state $H_t$, action $a_t$, a transition to $H_{t+1}$, repeated until a terminal action. That's an MDP with no reward signal and no gradient — the same object you built RL intuition for in Concepts 104–107, except here the "policy" is a frozen, pretrained LLM being steered by prompting rather than trained by a return signal. (RLHF and tool-use fine-tuning, later, close that loop by turning "did the agent get the right final answer" into an actual reward.)

**Why it matters / where it leads.** Every agent framework you'll touch (function calling, LangChain/LangGraph agents, OpenAI's tool-use API) is this loop plus engineering around it: how to constrain $a_t$ to a valid action schema, how to bound the loop length, how to keep $H_t$ from blowing past the context window (Concept 63's $O(n^2)$ problem shows up again here, now as "context grows every iteration"). Tomorrow's concept, multimodal models, is the natural next expansion of the *action space* itself — once a model can call a vision or audio tool, "observation" stops meaning "text back from an API" and starts meaning "pixels or waveforms back from a sensor."

## 🐍 PYTHONIC EDGE

Every agent needs a way to go from an action *name* (a string the model emitted) to the *function* that actually executes it. This is the textbook case for a dispatch table instead of a growing conditional.

```python
# ---- the bad way: if/elif chain (grows unbounded, one more elif per tool forever) ----
def call_tool_if_chain(name, **kwargs):     # **kwargs: sponge for arbitrary keyword args, no C++ equivalent without variadic templates
    if name == "search":
        return search_tool(**kwargs)
    elif name == "calculator":
        return calculator_tool(**kwargs)
    elif name == "python_exec":
        return python_exec_tool(**kwargs)
    else:
        raise ValueError(f"unknown tool: {name}")   # f-string: inline expression interpolation, no printf-style format specifiers needed

# ---- the clean way: a registry dict of first-class functions, populated by a decorator ----
TOOL_REGISTRY = {}                          # a plain dict standing in for a lookup table -- no template params, no header declaration

def tool(name):                             # a decorator *factory*: called with an argument, it returns the actual decorator
    def register(fn):                       # `fn` is the function being decorated -- functions are ordinary values here
        TOOL_REGISTRY[name] = fn            # storing a function itself in a dict; C++ needs std::function or a raw pointer to do this
        return fn
    return register

@tool("search")                             # equivalent to: search_tool = tool("search")(search_tool)
def search_tool(query: str, **kwargs):
    ...

@tool("calculator")
def calculator_tool(expr: str, **kwargs):
    ...

def dispatch(name, **kwargs):
    fn = TOOL_REGISTRY.get(name)            # .get returns None on a missing key instead of raising -- a built-in "safe lookup"
    if fn is None:
        raise ValueError(f"unknown tool: {name}")
    return fn(**kwargs)                     # **kwargs here *unpacks* the dict back into keyword arguments at the call site
```

The if/elif version means every new tool touches a shared function and risks merge conflicts; the registry version means adding a tool is a self-contained `@tool("name")` decoration with zero edits elsewhere — exactly the extensibility an agent framework needs when tools are being added by different people or plugged in dynamically at runtime.

## 📡 SIGNAL LAB

The agent's core decision — *"do I have enough evidence to answer, or do I call another tool?"* — is precisely **Wald's Sequential Probability Ratio Test (SPRT)**, a classic sequential-detection tool. In SPRT you're choosing between two hypotheses $H_0$ and $H_1$ from a *stream* of noisy observations, and instead of fixing the sample size in advance, you accumulate a log-likelihood ratio and stop the instant it's decisive:

$$\Lambda_t = \sum_{i=1}^{t} \log \frac{f_1(x_i)}{f_0(x_i)}, \qquad \text{stop and decide } H_1 \text{ if } \Lambda_t \ge \log\frac{1-\beta}{\alpha}, \quad \text{decide } H_0 \text{ if } \Lambda_t \le \log\frac{\beta}{1-\alpha}$$

where $\alpha, \beta$ are your tolerated false-accept/false-reject rates. This is exactly the agent's stopping rule, just with a formal guarantee attached: keep sampling (call another tool) while evidence is ambiguous, stop the moment accumulated evidence crosses a confidence boundary in either direction — and SPRT is provably the test that reaches a decision in the *fewest expected samples* for a given error rate, which is the same thing you want from an agent (minimum tool calls for a reliable answer).

**Worked example** — detect whether a sequence of noisy observations is being generated by $\mathcal{N}(1, 1)$ (signal present) vs $\mathcal{N}(0, 1)$ (signal absent), stopping as soon as the log-likelihood ratio is decisive:

```python
import numpy as np

np.random.seed(42)
alpha, beta = 0.05, 0.05
upper = np.log((1 - beta) / alpha)     # ~2.94: decisive evidence for H1
lower = np.log(beta / (1 - alpha))     # ~-2.94: decisive evidence for H0

true_theta = 1.0
samples = true_theta + np.random.randn(40)

llr = 0.0
for i, x in enumerate(samples, start=1):
    llr += x - 0.5                      # log f1(x)/f0(x) for unit-variance Gaussians centered at 1 and 0
    if llr >= upper:
        print(f"stopped at step {i}: accept H1 (signal present), LLR={llr:.2f}")
        break
    if llr <= lower:
        print(f"stopped at step {i}: accept H0 (signal absent), LLR={llr:.2f}")
        break
```

![SPRT log-likelihood-ratio walk crossing a decision boundary, analogous to an agent stopping to act](graph_DAY_109.png)

**So what:** the plot's random walk crossing a boundary *is* an agent's evidence accumulation made visual — every tool call is one more sample, and the walk should hit a boundary quickly when the tool results are informative, or wander indefinitely (your infinite-loop failure mode from the interview question) when they're not. If you ever build an agent that decides "should I call one more retriever/tool or answer now," SPRT-style thresholding on a calibrated confidence score is a principled alternative to "just cap the loop at N steps and hope."

## 🏋️ THE GAUNTLET

**Problem — Course Schedule II** *(an agent that must sequence dependent tool calls faces exactly this: which calls can run now, which must wait on another's result first)*

There are `numCourses` courses labeled `0` to `numCourses - 1`. You're given an array `prerequisites` where `prerequisites[i] = [a, b]` means course `b` must be completed before course `a`. Return **any** valid order to finish all courses, or an empty array if it's impossible (a cyclic dependency).

**Constraints:** `1 <= numCourses <= 2000`, `0 <= prerequisites.length <= 5000`.

**Hints (escalating):**
1. Model this as a directed graph. Which courses can obviously go *first* — the ones with no unmet prerequisites? What property of a node captures that?
2. Once you take a course, its dependents lose one unmet prerequisite. Maintain that count per node and process nodes whose count hits zero, using a queue to drive the order.
3. If a valid full order exists, how many nodes will you have processed by the end? What does it mean if your queue empties out before you've processed all `numCourses` nodes?

**Pattern:** topological sort via Kahn's algorithm (BFS on in-degrees). **Target complexity:** `O(V + E)`.

🔓 GAUNTLET SOLUTION

```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    vector<int> findOrder(int numCourses, vector<vector<int>>& prerequisites) {
        vector<vector<int>> adj(numCourses);
        vector<int> inDegree(numCourses, 0);

        for (auto& p : prerequisites) {
            int course = p[0], prereq = p[1];
            adj[prereq].push_back(course);   // prereq -> course edge
            inDegree[course]++;
        }

        queue<int> q;
        for (int i = 0; i < numCourses; i++) {
            if (inDegree[i] == 0) q.push(i);  // courses with no prerequisites can start immediately
        }

        vector<int> order;
        order.reserve(numCourses);

        while (!q.empty()) {
            int cur = q.front();
            q.pop();
            order.push_back(cur);

            for (int next : adj[cur]) {
                if (--inDegree[next] == 0) {   // this dependent's last prerequisite is now satisfied
                    q.push(next);
                }
            }
        }

        if ((int)order.size() != numCourses) {
            return {};   // fewer nodes processed than exist -> a cycle blocked full traversal
        }
        return order;   // O(V + E) time, O(V + E) space for the adjacency list
    }
};
```

💡 CONCEPT ANSWER

Fix the loop's structure, not its prompt:

- **Hard step cap** — cap total iterations (or total tokens spent in the loop) and force a `finish` (even a "couldn't determine an answer, here's what I found") once the cap is hit. This is the non-negotiable safety net underneath everything else.
- **Constrain the action schema** — force tool calls through a structured format (JSON schema / function-calling grammar) rather than free text, so "the same call with a slightly different query" is easier to detect as a near-duplicate action rather than a novel one.
- **State/action deduplication** — track a hash of `(tool_name, normalized_arguments)` already tried; if the model tries to repeat one, inject an explicit observation ("you already tried this and got X") instead of silently re-executing it, so the model is forced to change strategy.
- **Require progress justification** — before each tool call, make the model state (in a scratchpad field the loop can inspect, not just free reasoning text) what *new* information it expects that the last $k$ calls didn't already provide; if it can't articulate anything new, force a stop instead. This turns "no forward progress" from an implicit failure into a detectable, checkable condition — the same instinct as SPRT's explicit stopping rule above, applied to loop control instead of statistical evidence.
