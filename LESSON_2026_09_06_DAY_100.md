# Day 100 — KV Cache

## 🧠 CONCEPT OF THE DAY

**Intuition.** Picture a courtroom stenographer who, instead of keeping a running transcript, re-transcribes the entire proceeding from the gavel every time a new word is spoken — word 500 costs as much work as words 1 through 499 combined, all over again. That's exactly what naive autoregressive decoding does to itself. To predict token `t+1`, causal self-attention at every layer needs the Key and Value vectors for *every* token `1..t` — but tokens `1..t` never change once they've been generated. A **KV cache** is just the fix: compute each token's K and V vectors once, the moment it's generated, store them, and on every later step only compute K/V for the one brand-new token, appending it to the cache instead of recomputing anything that's already settled.

**The math.** At layer `l`, token `i` has hidden state `h_i`, projecting to `K_i = h_i W_K` and `V_i = h_i W_V`. Causal attention for the token currently being generated (position `t`) is:

$$\text{Attn}(Q_t, K_{1:t}, V_{1:t}) = \text{softmax}\!\left(\frac{Q_t K_{1:t}^\top}{\sqrt{d_k}}\right) V_{1:t}$$

Without a cache, producing token `T` means re-running the *entire* network on tokens `1..T` from scratch — hidden states at every layer depend on all previous layers, so you're redoing every linear projection and FFN for every past position, every step. That per-step cost is `O(T · d_model²)`, and summed over `T` generation steps it's `O(T² · d_model²)` total: quadratic in sequence length, for work that produces the *same numbers* every time. With a cache, each step only pushes the one new token through the network — `O(d_model²)` of fresh projection/FFN work per step — while reusing cached `K_{1:t-1}, V_{1:t-1}` and appending the new pair. Summed over `T` steps that's `O(T · d_model²)`: linear. The attention score computation itself, `Q_t` against all `t` cached keys, stays `O(t · d)` per step either way — that's the same `O(n²)`-over-a-generation attention cost you met back in Concept 63, and caching doesn't touch it. What caching eliminates is the *redundant re-derivation of K and V*, not attention's inherent quadratic footprint.

The other half of the story is memory, not compute. Per sequence, the cache holds two tensors (K and V) at every layer, for every cached position:

$$\text{KV cache bytes} = 2 \cdot L \cdot T \cdot d_{model} \cdot p$$

where `L` = layers, `T` = tokens cached so far, `d_model = H · d_h` (heads × head-dim), `p` = bytes per stored element (2 for fp16/bf16), and the leading 2 is for K *and* V. Plug in a Llama-2-7B-shaped model (`L=32`, `d_model=4096`, fp16) at `T=4096`: `2·32·4096·4096·2 ≈ 2.1×10⁹` bytes ≈ **2 GiB — per single sequence**, before a single activation or attention score is stored.

![Non-attention compute (cached vs. uncached decoding) and KV cache memory vs. context length for a 7B-class model](graph_DAY_100.png)

Left panel: cached decoding's per-step work stays flat while uncached decoding's grows linearly with position, so the *cumulative* gap is quadratic vs. linear — exactly the compute argument above. Right panel: even with caching solving compute, memory still grows linearly in context length, and at long contexts or many concurrent requests that linear growth adds up fast — 32 concurrent 4096-token sequences on that same model need **~64 GiB** just for KV cache, on top of the model's own ~14 GiB of fp16 weights.

**Why it matters / where it leads.** This is why, in production serving, the KV cache — not the model weights — is usually the resource you run out of first. It's the direct motivation for tomorrow's throughput-vs-latency and batching discussion (max concurrent batch size is usually KV-cache-bound, not weight-memory-bound), and for a family of techniques you'll meet down the line: PagedAttention (vLLM) manages KV cache like an OS manages virtual memory pages instead of one contiguous blob per sequence; Multi-Query and Grouped-Query Attention shrink the cache by sharing K/V heads across multiple Q heads; quantized (int8/int4) KV caches trade a little precision for a lot of headroom. None of these change what attention computes — they all attack the same `2·L·T·d_model·p` bill from a different angle.

**Interview question:** *You're serving a 13B-parameter decoder-only model: 40 layers, `d_model=5120` (40 heads × head_dim 128), fp16 weights and fp16 KV cache, on an 80GB GPU where the weights already take 26GB. At what context length does ONE sequence's KV cache exceed 1 GiB? Given the 54GB left after weights, roughly how many concurrent sequences at 2048-token context can you serve before KV cache alone exhausts it — and name one architectural lever that shrinks the cache without changing what attention computes.*

## 🐍 PYTHONIC EDGE

The bad way calls the model on the *entire* growing sequence every step; the clean way threads a cache tuple through and only ever feeds the model one new token.

```python
import torch
import torch.nn as nn

class ToyCausalAttention(nn.Module):                        # class X(Base): single inheritance -- C++: class X : public Base
    def __init__(self, d_model, n_heads):                    # self is explicit -- C++'s implicit `this`
        super().__init__()                                   # parent ctor call; C++ uses initializer-list syntax instead
        self.n_heads = n_heads                                # self.x = ... sets an instance attribute --
        self.d_head = d_model // n_heads                      # C++ declares in the header, inits in the body
        self.qkv = nn.Linear(d_model, 3 * d_model)            # // is floor division -- no bare C++ equivalent for ints
        self.out = nn.Linear(d_model, d_model)

    def forward(self, x, kv_cache=None):                      # kv_cache=None -- keyword arg with a default,
        B, T, D = x.shape                                     # None is Python's null singleton, no nullptr distinction
        q, k, v = self.qkv(x).chunk(3, dim=-1)                # tuple unpacking (a, b, c = ...) -- no C++ equivalent
        if kv_cache is not None:                              # without std::tie; dim=-1 -- negative axis index, "last dim"
            k_prev, v_prev = kv_cache                         # `is not None`, never `!= None` -- identity check on the singleton
            k = torch.cat([k_prev, k], dim=1)                 # torch.cat concatenates along the sequence axis --
            v = torch.cat([v_prev, v], dim=1)                 # this is the entire "append to cache" operation
        new_cache = (k, v)                                    # tuple literal -- an immutable pair, no struct needed
        attn = (q @ k.transpose(-2, -1)) / self.d_head ** 0.5 # @ is matmul (not C++'s bitwise &); ** is exponentiation (not xor)
        # causal mask omitted for brevity -- production code masks future positions here
        y = self.out(attn.softmax(dim=-1) @ v)
        return y, new_cache                                    # called via __call__, which wraps forward() with hooks --
                                                                # never invoke .forward() directly

# ---- the bad way: recompute the whole prefix every single step ----
def generate_no_cache(model, tokens, steps):
    for _ in range(steps):                                     # range() is a lazy iterator object, not a materialized list
        y, _ = model(tokens)                                    # re-runs attention over the ENTIRE growing sequence, every step
        next_token = y[:, -1:, :]                               # [-1:] -- negative-index slice, "last position onward";
        tokens = torch.cat([tokens, next_token], dim=1)         # C++ has no slice syntax, this needs manual index math

# ---- the clean way: carry the cache forward, feed only the new token ----
def generate_with_cache(model, tokens, steps):
    y, cache = model(tokens)                                    # one full pass over the prompt populates the cache
    next_token = y[:, -1:, :]
    for _ in range(steps - 1):
        y, cache = model(next_token, kv_cache=cache)             # only ONE new token goes through the network per step
        next_token = y[:, -1:, :]                                 # cache grows by one slot; nothing already cached is redone
```

`generate_no_cache` is `O(T²)` in exactly the way the concept section derived; `generate_with_cache` is the `O(T)` version, and the only code-level difference is threading `kv_cache` through instead of re-passing `tokens`.

## 📡 SIGNAL LAB

The KV cache's "store what's already computed, only extend it" discipline has an exact DSP analog: a streaming FIR filter's **delay line**. Direct convolution recomputes the full sliding window from raw samples every output; a streaming implementation keeps only the last `(len(h)-1)` input samples as state and updates that state incrementally — never re-touching samples that already left the window.

**Worked mini-example.** Filter `h = [1, 0.5, 0.25]` (length 3), streaming input arriving one sample at a time: `x = [1, 2, 3, 4]`. Maintain a delay line `d = [0, 0]` (two past samples, since `len(h)-1 = 2`).

Step-by-step, output `y_n = h_0 x_n + h_1 d_0 + h_2 d_1`, then shift `d ← [x_n, d_0]`:

- `n=0`: `x_0=1`, `d=[0,0]` → `y_0 = 1·1 + 0.5·0 + 0.25·0 = 1`; update `d=[1,0]`
- `n=1`: `x_1=2`, `d=[1,0]` → `y_1 = 1·2 + 0.5·1 + 0.25·0 = 2.5`; update `d=[2,1]`
- `n=2`: `x_2=3`, `d=[2,1]` → `y_2 = 1·3 + 0.5·2 + 0.25·1 = 4.25`; update `d=[3,2]`
- `n=3`: `x_3=4`, `d=[3,2]` → `y_3 = 1·4 + 0.5·3 + 0.25·2 = 6.0`; update `d=[4,3]`

Check against direct convolution of the full signal with `h`: `y = x * h` gives `[1, 2.5, 4.25, 6.0, ...]` for the first four outputs — identical, and at no point did the streaming version re-touch a sample once it left the two-slot delay line.

**So what:** this is the KV cache's discipline, one abstraction level down — a delay line *is* a cache of exactly the state needed to produce the next output, nothing more. For frequency-domain generative-forensics work specifically, this is why real-time streaming STFT (for live spectrogram-based deepfake detection, say) carries forward only the current window's overlap samples between frames rather than recomputing the transform over the entire elapsed signal — the same `O(T²) → O(T)` collapse, for a spectral transform's state instead of a transformer's.

## 🏋️ THE GAUNTLET

**LRU Cache**

Design a cache with a fixed capacity `k` supporting two operations, both required to run in `O(1)` time:
- `get(key)`: return the value if `key` exists in the cache, else `-1`. Accessing a key counts as "using" it (marks it most-recently-used).
- `put(key, value)`: insert or update the value for `key`. If inserting exceeds capacity, evict the **least recently used** key first.

This is exactly the eviction problem real KV-cache-serving engines (vLLM, TGI) solve at the GPU-memory level when concurrent requests exceed available cache blocks — which entry gets kicked out when something new needs room.

Constraints:
- `1 <= capacity <= 3000`
- up to `2 × 10^5` calls to `get` and `put` combined
- `0 <= key, value <= 10^4`

**Hints (escalating):**
1. You need O(1) lookup by key *and* O(1) knowledge of what's least-recently-used — no single standard container gives you both.
2. A hash map gives O(1) key→something lookup. For O(1) recency tracking, you need a structure where moving an element to the "most recent" end doesn't require shifting anything else — an array can't do that in O(1), but a doubly linked list can, given a direct pointer to the node.
3. Combine them: hash map from `key` to a pointer/iterator into a doubly linked list ordered by recency. On every `get`/`put` that touches an existing key, splice that node out and re-insert it at the front in O(1) — no other node's position changes, so no other iterator is invalidated.

**Pattern:** hash map + doubly linked list (the LRU pattern). **Target complexity:** `O(1)` per operation, `O(k)` space.

## 🔓 GAUNTLET SOLUTION

```cpp
#include <bits/stdc++.h>
using namespace std;

class LRUCache {
    int capacity;
    list<pair<int,int>> items;                         // front = most recent, back = least recent
    unordered_map<int, list<pair<int,int>>::iterator> lookup;

public:
    LRUCache(int capacity) : capacity(capacity) {}

    int get(int key) {
        auto it = lookup.find(key);
        if (it == lookup.end()) return -1;
        items.splice(items.begin(), items, it->second);   // move node to front in O(1), no invalidation
        return it->second->second;
    }

    void put(int key, int value) {
        auto it = lookup.find(key);
        if (it != lookup.end()) {
            it->second->second = value;
            items.splice(items.begin(), items, it->second);
            return;
        }
        if ((int)items.size() == capacity) {
            int lruKey = items.back().first;
            items.pop_back();
            lookup.erase(lruKey);
        }
        items.emplace_front(key, value);
        lookup[key] = items.begin();
    }
};
```

Correctness: `list::splice` moves a node between positions (or within the same list) in O(1) without invalidating iterators to it or to any other node — that's precisely what lets the map's stored iterators stay valid across arbitrary reorderings. Every `get`/`put` on an existing key does exactly one splice; every eviction removes exactly `items.back()`, which is maintained as the least-recently-used entry by construction (everything touched moves to the front, so the back is always what's gone longest untouched). Both operations are O(1) amortized: one hash lookup plus one O(1) list splice.

## 💡 CONCEPT ANSWER

Bytes per token across all layers: `2 · L · d_model · p = 2 · 40 · 5120 · 2 = 819,200 bytes ≈ 800 KB/token`. Exceeding 1 GiB (`1,073,741,824` bytes) needs `1,073,741,824 / 819,200 ≈ 1310.7` → **at ~1311 tokens of context, one sequence's KV cache alone passes 1 GiB.**

At 2048-token context, one sequence's cache is `819,200 × 2048 ≈ 1.68×10⁹` bytes ≈ **1.56 GiB**. With 54 GB left after the 26 GB of weights: `54 × 1024³ / (819,200 × 2048) ≈ 34.6` → **roughly 34 concurrent sequences** before KV cache alone exhausts the remaining memory (and that's before leaving any room for activations, so a real deployment would cap well below this).

Architectural lever: **Grouped-Query Attention (GQA)** (or its extreme, Multi-Query Attention) — share a small number of KV heads across groups of query heads instead of one KV head per query head. Going from 40 KV heads to, say, 8 shared KV heads divides the `2·L·T·d_model` term by 5× directly (the cache only needs to store `d_model_kv = 8·128 = 1024`-wide K/V instead of the full `5120`-wide version), multiplying the ~34-sequence ceiling by roughly the same factor — without changing the attention computation's mathematical shape or the query-side capacity of the model at all.
