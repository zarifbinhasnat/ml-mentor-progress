## 🧠 CONCEPT OF THE DAY

**Intuition.** Imagine solving a long proof one line at a time, and at every new line you re-derive the *entire* proof from scratch instead of just referencing what you already wrote down. That's a naive autoregressive decoder: to generate token `t+1`, it feeds the whole sequence `1..t` back through the model and only keeps the last position's output. Every previous token gets fully re-processed, forever, even though nothing about its representation has changed (causal masking guarantees token `i`'s hidden state never depends on tokens after it). The KV cache is just "write it down instead of re-deriving it": once a token's Key and Value vectors are computed at a given layer, they're frozen for the rest of generation, so we store them and only compute Q/K/V for the *new* token each step.

**The math.** Recall scaled dot-product attention at layer `l`, step `t`:

$$\text{Attn}(q_t, K_{1:t}, V_{1:t}) = \text{softmax}\left(\frac{q_t K_{1:t}^\top}{\sqrt{d_k}}\right) V_{1:t}$$

where $q_t = W_Q x_t$ is the new token's query, and $K_{1:t}, V_{1:t}$ are the keys/values for *all* tokens seen so far. Without caching, computing $K_{1:t}, V_{1:t}$ means re-running $W_K x_i, W_V x_i$ (and every layer beneath it) for every $i \le t$ — that's $O(t)$ full-network work per step, and summed over generating $n$ tokens:

$$\text{Total naive cost} = \sum_{t=1}^{n} O(t) = O(n^2)$$

With a KV cache, at step $t$ we only compute $k_t = W_K x_t$, $v_t = W_V x_t$ for the *new* token, append them:

$$K_{1:t} = [K_{1:t-1} \,;\, k_t], \qquad V_{1:t} = [V_{1:t-1} \,;\, v_t]$$

and reuse the untouched $K_{1:t-1}, V_{1:t-1}$. Per-step cost drops to $O(1)$ full-network work plus an $O(t)$ attention dot-product (cheap relative to the full stack — it's one matmul against cached vectors, not a re-run of every layer). Total cost across $n$ steps becomes $O(n)$ dominant, with the attention term contributing only a low-constant $O(n^2)$ that's negligible in practice.

![Decode compute (naive vs KV cache) and KV cache memory growth](graph_DAY_100.png)

**The catch — and why it matters.** You didn't eliminate the cost, you moved it: from *recomputed FLOPs* to *stored memory*. KV cache size scales as

$$\text{bytes} = 2 \times L \times H \times d_{\text{head}} \times T \times \text{batch} \times \text{dtype\_size}$$

($2$ for K and V, $L$ layers, $H$ heads, $d_{\text{head}}$ per-head dim, $T$ sequence length so far). That's *linear in sequence length* and *linear in batch size* — and for a 7B-class model at long context, the cache alone can exceed the model's own weight memory. This is exactly why context length is a serving-cost problem, not just a "can the model attend that far" problem, and it's the direct setup for Concept 101 (throughput vs. latency — cache size caps how many sequences you can batch concurrently) and Concept 103 (vLLM's PagedAttention, which manages this cache like an OS manages virtual memory pages instead of one contiguous allocation per sequence).

## 🐍 PYTHONIC EDGE

The naive way people implement a "cache" in a decoding loop is to grow a tensor with `torch.cat` every step — which defeats half the point, because `cat` allocates a brand-new tensor and copies the *entire* existing cache into it every single call. That's $O(t)$ copy work per step, i.e. you've reintroduced an $O(n^2)$ cost, just in memory bandwidth instead of FLOPs.

```python
# BAD: torch.cat every decode step
def update_cache_bad(cache, new_kv):
    return torch.cat([cache, new_kv], dim=2)   # dim=2 is the sequence axis (0-indexed, like C++)
    # torch.cat always allocates a fresh tensor and copies the old + new data in —
    # calling this n times to grow a length-n cache costs O(n^2) total memory traffic

# GOOD: preallocate the max-length buffer once, then write in place by index
class KVCache:                                  # class KVCache:  (no "(Base)" -> implicitly inherits object; C++: no ": public Base")
    def __init__(self, max_len, n_heads, head_dim, dtype=torch.float16):
        # __init__ is the constructor; `self` is explicit here (C++'s implicit `this`,
        # but Python never hides it — every method takes it as the first param)
        self.k = torch.zeros(1, n_heads, max_len, head_dim, dtype=dtype)
        self.v = torch.zeros(1, n_heads, max_len, head_dim, dtype=dtype)
        # self.k = ... creates an instance attribute on the fly
        # (C++: you'd declare the member in the class body, then assign in the ctor)
        self.pos = 0                             # no type declaration needed — Python attributes are dynamically typed

    def update(self, k_new, v_new):
        t = k_new.shape[2]                       # .shape indexes like a tuple; [2] is a plain 0-based index
        self.k[:, :, self.pos:self.pos + t] = k_new   # slice assignment (a:b) writes in place — no new allocation
        self.v[:, :, self.pos:self.pos + t] = v_new
        self.pos += t                             # += works the same as in C++
        return self.k[:, :, :self.pos], self.v[:, :, :self.pos]   # [:x] slices "from the start up to x"
```

This is not a toy simplification — HuggingFace's `StaticCache` and llama.cpp's KV buffers work exactly this way: preallocate for `max_len`, write by index, never reallocate mid-generation. It's also what makes `torch.compile`/CUDA-graph-friendly decoding possible — a shape that never changes is a graph that can be captured once and replayed.

## 📡 SIGNAL LAB

The KV cache is really just a general "don't recompute what's causally frozen" pattern — and DSP has been doing this for decades under the name **overlap-save block convolution**.

**Setup:** you're filtering a streaming signal with an FIR filter of length $M$, but the signal arrives in blocks of $N$ new samples at a time, and you want to filter causally without ever touching samples that already left the pipeline. The naive approach: every time a new block arrives, concatenate it to *everything* you've received so far and reconvolve the whole history — cost grows as $O(n^2)$ in total samples processed, identical in shape to naive re-encoding.

**The cache-based fix:** an FIR filter's output at time $i$ only depends on the current sample and the previous $M-1$ samples (its "memory"). So instead of storing full history, you cache exactly that tail:

```python
import numpy as np

def stream_convolve(signal, h, block_size):
    M = len(h)
    tail = np.zeros(M - 1)          # the "cache": last M-1 samples from the previous block
    out = []
    for start in range(0, len(signal), block_size):
        block = signal[start:start + block_size]
        extended = np.concatenate([tail, block])      # cache + new data only — never the full history
        y = np.convolve(extended, h, mode="full")
        out.append(y[M - 1 : M - 1 + len(block)])      # the causally-valid, non-overlapping part
        tail = extended[-(M - 1):]                      # refresh the cache for next block
    return np.concatenate(out)

np.random.seed(42)
signal = np.random.randn(64)
h = np.array([0.2, 0.5, 0.2, 0.1])   # length-4 FIR filter -> cache size 3

streamed = stream_convolve(signal, h, block_size=8)
reference = np.convolve(signal, h, mode="full")[: len(signal)]
print(np.allclose(streamed, reference, atol=1e-10))   # True
```

**So what:** the tail buffer here is doing precisely what the KV cache does — it's the minimal causally-sufficient state that lets you process new input without re-touching old input. Both are instances of the same idea: *a system with finite causal memory only needs to carry forward that memory, not its full history*. When you get to FlashAttention-style kernels later (and eventually streaming/chunked attention for long-context models), you'll see this exact "carry forward a fixed-size running state instead of the full history" trick again, just dressed up as running softmax statistics instead of a filter tail.

## 🏋️ THE GAUNTLET

**Problem — LRU Cache (LeetCode 146).**
Design a data structure that implements a Least Recently Used (LRU) cache with a fixed capacity `capacity`. It must support:
- `get(key)` — return the value if the key exists, else `-1`. Using a key counts as "recently used."
- `put(key, value)` — insert or update the value. If inserting causes the cache to exceed `capacity`, evict the least recently used entry first.

Both operations must run in **O(1) average time**.

**Constraints:** `1 <= capacity <= 3000`, up to `2 * 10^5` calls to `get`/`put`, key/value fit in a 32-bit signed int.

**Hint 1:** A hash map alone gives you O(1) lookup, but it can't tell you *usage order* — you need a second structure that tracks recency and supports O(1) "move this to the front" and O(1) "remove the back."

**Hint 2:** A doubly linked list gives O(1) removal/insertion at arbitrary nodes *if you already have a pointer to the node* — which is exactly what the hash map should store: `key -> node pointer`, not `key -> value`.

**Hint 3:** Maintain the list ordered from most-recently-used (head) to least-recently-used (tail), with sentinel head/tail nodes to avoid null-pointer edge cases on empty/single-element lists. Every `get`/`put` on an existing key unlinks its node and re-inserts it right after the head.

**Pattern:** Hash Map + Doubly Linked List. **Target complexity:** O(1) per operation, O(capacity) space.

## 🔓 GAUNTLET SOLUTION

```cpp
class LRUCache {
private:
    struct Node {
        int key, value;
        Node* prev;
        Node* next;
        Node(int k, int v) : key(k), value(v), prev(nullptr), next(nullptr) {}
    };

    int capacity;
    unordered_map<int, Node*> map;   // key -> node pointer, O(1) lookup
    Node* head;   // sentinel: head->next is most recently used
    Node* tail;   // sentinel: tail->prev is least recently used

    void remove(Node* node) {
        node->prev->next = node->next;
        node->next->prev = node->prev;
    }

    void insertAtFront(Node* node) {
        node->next = head->next;
        node->prev = head;
        head->next->prev = node;
        head->next = node;
    }

public:
    LRUCache(int capacity) : capacity(capacity) {
        head = new Node(-1, -1);
        tail = new Node(-1, -1);
        head->next = tail;
        tail->prev = head;
    }

    int get(int key) {
        if (map.find(key) == map.end()) return -1;
        Node* node = map[key];
        remove(node);
        insertAtFront(node);   // using it makes it most-recently-used
        return node->value;
    }

    void put(int key, int value) {
        if (map.find(key) != map.end()) {
            Node* node = map[key];
            node->value = value;
            remove(node);
            insertAtFront(node);
            return;
        }
        if ((int)map.size() == capacity) {
            Node* lru = tail->prev;      // least recently used = right before tail sentinel
            remove(lru);
            map.erase(lru->key);
            delete lru;
        }
        Node* node = new Node(key, value);
        insertAtFront(node);
        map[key] = node;
    }
};
```

Both `get` and `put` do a fixed number of hash-map and pointer operations — O(1) amortized, O(capacity) space for the map and list nodes.

## 💡 CONCEPT ANSWER

**KV cache memory:** bytes $= 2 \times L \times H \times d_{\text{head}} \times T \times \text{batch} \times \text{dtype\_bytes}$
$= 2 \times 32 \times 32 \times 128 \times 8192 \times 16 \times 2 \text{ bytes (fp16)}$
$\approx 2 \times 32 \times 32 \times 128 \times 8192 \times 16 \times 2 = 68{,}719{,}476{,}736 \text{ bytes} \approx 68.7\text{ GB}$.

That alone can exceed the memory of several high-end GPUs, before you've stored a single model weight.

**Why doubling context hurts more than doubling parameters, memory-wise:** model weights are a **fixed** cost paid once regardless of batch size or sequence length — double the parameters and memory roughly doubles, once. But the KV cache scales with $T \times \text{batch}$: doubling context length doubles the cache for *every concurrent request*, and that multiplies against however many sequences you're trying to batch together for throughput. So a longer context doesn't just cost more memory in isolation — it directly shrinks your maximum serving batch size (or forces you to evict/page cache, as in vLLM's PagedAttention), which is a throughput hit on top of the raw memory hit. Parameter count is a one-time tax; context length is a tax multiplied by every request you're trying to serve concurrently.
