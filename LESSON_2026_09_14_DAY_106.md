# Day 106 — Policy gradients / REINFORCE

## 🧠 CONCEPT OF THE DAY

**Intuition.** Yesterday's DQN learned a value $Q(s,a)$ and only acted *indirectly* — pick whatever action the argmax happens to point at. Policy gradients throw that intermediary away and parametrize the decision-making itself: a policy $\pi_\theta(a\mid s)$ that directly outputs a distribution over actions. Training is trial-and-error at the trajectory level — like a coach who never lectures on theory, just watches the whole game unfold and afterward nudges every decision that led to a win to be *more* likely next time, and every decision that led to a loss to be *less* likely, in proportion to how good or bad the final outcome was. No value function is required to make this correction; you only need to have *sampled* an outcome.

**The math.** The objective is the expected return over trajectories $\tau=(s_0,a_0,s_1,a_1,\dots)$ sampled by running the policy:

$$J(\theta) = \mathbb{E}_{\tau \sim \pi_\theta}\big[R(\tau)\big]$$

You can't backprop through the environment (it's not differentiable, and often not even known), so directly differentiating $J$ seems stuck. The fix is the **score-function estimator** (a.k.a. the log-derivative trick): for any distribution $p_\theta$,

$$\nabla_\theta \, \mathbb{E}_{x\sim p_\theta}[f(x)] = \mathbb{E}_{x\sim p_\theta}\big[f(x)\,\nabla_\theta \log p_\theta(x)\big]$$

which only needs $p_\theta$ to be differentiable — $f$ itself (here, the environment's reward) can be an arbitrary black box. Applying this per-timestep gives the **policy gradient theorem**:

$$\nabla_\theta J(\theta) = \mathbb{E}_{\tau\sim\pi_\theta}\Big[\sum_t \nabla_\theta \log \pi_\theta(a_t\mid s_t)\, G_t\Big], \qquad G_t = \sum_{k\ge t}\gamma^{k-t} r_k$$

where $G_t$ is the return-to-go from time $t$. **REINFORCE** is just Monte Carlo estimation of that expectation: roll out full episodes under the current $\pi_\theta$, compute each $G_t$, and take a gradient step $\theta \leftarrow \theta + \alpha\sum_t \nabla_\theta \log \pi_\theta(a_t\mid s_t)\,G_t$. Read the update as: whichever action you *actually took*, push $\theta$ to make it more likely if $G_t$ was large, less likely if $G_t$ was small or negative — the gradient literally is "log-probability of what happened, scaled by how good it turned out."

The catch is variance: $G_t$ is a noisy Monte Carlo sample of a whole future, so the raw estimator above swings wildly between episodes. A standard fix is subtracting a **baseline** $b(s_t)$ (commonly an estimate of $V^\pi(s_t)$) from $G_t$: $\mathbb{E}\big[\nabla_\theta\log\pi_\theta(a\mid s)\,b(s)\big]=0$ for any state-only $b(s)$, since $\int_a \pi_\theta(a\mid s)\nabla_\theta \log\pi_\theta(a\mid s)\,da = \nabla_\theta\int_a\pi_\theta(a\mid s)\,da=\nabla_\theta 1 = 0$ — so a baseline is unbiased *by construction*, while cutting variance whenever $b(s)$ tracks the typical scale of $G_t$ at that state.

**Why it matters / where it leads.** Policy gradients handle continuous action spaces naturally (no argmax over an infinite action set, unlike DQN) and optimize the *actual* quantity you care about — expected return — directly, rather than through a value-function proxy. But REINFORCE is on-policy (every gradient step needs fresh trajectories from the current $\theta$; you can't reuse old data the way replay buffers do) and high-variance even with a baseline. Tomorrow's actor-critic/PPO (107) is exactly the fix: replace the Monte Carlo $G_t$ with a learned, bootstrapped critic — value-based and policy-based RL fusing into one method. This derivation — score function estimator, baseline, why it's unbiased — is one of the most common RL interview screens, because it separates people who've memorized "REINFORCE = log-prob times reward" from people who understand *why* that's a valid gradient at all.

**Interview-style question:** *Why can you subtract a baseline $b(s)$ from the return $G_t$ in the REINFORCE update without changing the expected gradient, and why does it reduce variance in practice even though it changes nothing in expectation?*

## 🐍 PYTHONIC EDGE

The most common REINFORCE bug: manually computing action probabilities and log-probs by hand instead of using `torch.distributions`, which is both cleaner and more numerically stable (it fuses log-softmax internally instead of doing `log(softmax(x))`, which can blow up for confident/near-zero probabilities).

```python
import torch
import torch.nn as nn
from torch.distributions import Categorical  # import X (submodule) -- no C++ header-only equivalent

class PolicyNet(nn.Module):        # single inheritance (C++: class PolicyNet : public nn::Module)
    def __init__(self, obs_dim, n_actions):   # constructor; self is explicit here (C++'s `this` is implicit)
        super().__init__()          # runs nn.Module's ctor first (C++: initializer-list syntax instead)
        self.fc = nn.Linear(obs_dim, n_actions)  # instance attr; C++ declares in header, inits in body

    def forward(self, x):           # never call this directly
        return self.fc(x)           # returns raw logits, not probabilities

policy_net = PolicyNet(obs_dim=4, n_actions=2)
state = torch.randn(1, 4)

# ---- BAD: manual softmax + log + index, fragile and easy to get subtly wrong ----
logits = policy_net(state)                    # __call__ wraps forward() with hooks -- never call .forward() directly
probs = torch.softmax(logits, dim=-1)         # dim=-1: last axis, negative indexing again (Python-only convention)
action = torch.multinomial(probs, 1).item()   # .item() unboxes a 1-element tensor to a plain Python scalar
log_prob_bad = torch.log(probs[0, action])    # manual log after softmax -- can underflow for near-0 probabilities

# ---- CLEAN: let torch.distributions own sampling + log-prob together ----
dist = Categorical(logits=policy_net(state))  # logits=... keyword arg; class built directly from logits
action = dist.sample()                        # returns a tensor, shape (1,) -- not a Python int, no .item() needed
log_prob = dist.log_prob(action)              # fused, numerically-stable log-softmax + gather in one call

# ---- the REINFORCE loss, one episode's worth ----
log_probs = []                                # collected each step during the rollout, one per timestep
rewards = []                                  # ditto -- the raw per-step reward, not yet a return
for t in range(episode_len):                  # range() is a lazy object here, not a materialized list
    dist_t = Categorical(logits=policy_net(states[t]))
    a_t = dist_t.sample()
    log_probs.append(dist_t.log_prob(a_t))

returns, G = [], 0.0
for r in reversed(rewards):                   # walk backward: G_t = r_t + gamma * G_{t+1}
    G = r + GAMMA * G
    returns.insert(0, G)
returns = torch.tensor(returns)               # a constant target -- no grad_fn, nothing to detach

loss = -(torch.stack(log_probs) * returns).mean()  # negative: torch minimizes, we want to MAXIMIZE expected return
loss.backward()                               # backprop flows only through log_prob, never through returns
```

`Categorical` (and its continuous cousin `Normal` for continuous-action policies) is the idiom any time a network's output *is* a probability distribution you both sample from and score — manual softmax-then-index is the tell that someone hasn't reached for `torch.distributions` yet.

## 📡 SIGNAL LAB

Look at the REINFORCE gradient estimator itself: $\hat{g} = \frac{1}{N}\sum_{i=1}^N \nabla_\theta\log\pi_\theta(a_i\mid s_i)\,G_i$, averaged over $N$ sampled trajectories in a batch. Each trajectory's contribution is one noisy realization of the true gradient, and averaging $N$ i.i.d. noisy estimates cuts variance by a factor of $N$: $\mathrm{Var}(\hat{g}) = \mathrm{Var}(g)/N$. That is *exactly* the variance-reduction law behind **Welch's method** for power spectral density estimation: a single periodogram (one FFT of the whole signal) is a wildly noisy PSD estimate — its variance doesn't shrink as you collect more samples of a stationary noise process, it just gets finer *frequency resolution*. Welch's method instead splits the signal into $K$ segments, computes a periodogram per segment, and *averages* them — trading frequency resolution (shorter segments = wider bins) for a $1/K$ reduction in variance, the same knob REINFORCE turns when you increase the batch size $N$.

**Worked example.** The left panel of the graph below simulates a 2-armed logistic bandit with a fixed policy parameter $\theta$: reward $r(a{=}0)=1$, $r(a{=}1)=0$, so the single-sample REINFORCE gradient $g = r(a)\cdot\nabla_\theta\log\pi_\theta(a)$ is a genuinely noisy 2-valued random variable. Averaging $N$ i.i.d. samples of $g$ (i.e., $N$ trajectories per policy update) empirically tracks $\mathrm{Var}(g)/N$ almost exactly, confirmed on a log-log plot where the $1/N$ line is a straight line of slope $-1$. The right panel computes a single periodogram versus an 8-segment Welch-averaged periodogram of the same noisy sinusoid: the single periodogram's noise floor is jagged and swings over two orders of magnitude bin-to-bin, while the Welch average is visibly smoother — same $1/K$ law, same tradeoff (segment length ↔ batch size, both controlling variance vs. resolution/gradient-freshness).

![Left: REINFORCE gradient-estimate variance vs. batch size N, matching the Var(g)/N theory line on a log-log plot. Right: single periodogram vs. 8-segment Welch-averaged periodogram of a noisy sinusoid, showing the same variance-reduction-by-averaging law in the frequency domain.](graph_DAY_106.png)

**So what.** This is the same reason your PSD estimates get noisy with short, non-averaged FFTs and the same reason REINFORCE needs large batches (or many parallel environments) to train stably: neither problem is fixed by "a smarter estimator" alone — both are fundamentally trading sample count for variance, at a fixed $1/N$ (or $1/K$) rate. When you tune batch size in an RL codebase, you're turning the identical dial you already understand from choosing segment length and overlap in `scipy.signal.welch`.

## 🏋️ THE GAUNTLET

**Course Schedule (Can Finish All Courses?).** You're given `numCourses` courses labeled `0` to `numCourses - 1`, and a list `prerequisites` where `prerequisites[i] = [a, b]` means you must take course `b` before course `a`. Return `true` if it's possible to finish all courses, `false` otherwise.

Constraints: $1 \le \texttt{numCourses} \le 2\times10^5$, $0 \le \texttt{prerequisites.length} \le 5\times10^5$.

**Hint 1:** Model this as a directed graph where an edge `b -> a` means "b must come before a." Finishing all courses is possible if and only if this graph has no cycle — a prerequisite cycle means every course in it depends on itself finishing first.

**Hint 2:** Detecting a cycle without recursion depth blowing up on $2\times10^5$ nodes calls for **Kahn's algorithm**: compute in-degree for every node, push all in-degree-0 nodes into a queue, and repeatedly pop a node, "remove" its outgoing edges (decrement neighbors' in-degree), and push any neighbor that newly hits in-degree 0.

**Hint 3:** This is exactly BFS-based topological sort. If you can dequeue all `numCourses` nodes, there's no cycle and a valid ordering exists; if the queue empties early, whatever's left is stuck in a cycle (or depends on one).

**Pattern:** topological sort via Kahn's algorithm (BFS on in-degrees). **Target complexity:** $O(V+E)$ time, $O(V+E)$ space.

🔓 GAUNTLET SOLUTION

```cpp
#include <vector>
#include <queue>
using namespace std;

bool canFinish(int numCourses, vector<vector<int>>& prerequisites) {
    vector<vector<int>> adj(numCourses);
    vector<int> indegree(numCourses, 0);

    for (auto& p : prerequisites) {
        int a = p[0], b = p[1];       // b -> a: b must come before a
        adj[b].push_back(a);
        ++indegree[a];
    }

    queue<int> q;
    for (int i = 0; i < numCourses; ++i)
        if (indegree[i] == 0) q.push(i);   // no prerequisites left to satisfy

    int visited = 0;
    while (!q.empty()) {
        int node = q.front(); q.pop();
        ++visited;
        for (int next : adj[node]) {
            if (--indegree[next] == 0) q.push(next);  // just became unblocked
        }
    }

    return visited == numCourses;  // fewer than all nodes visited => a cycle exists somewhere
}
```

Classic Kahn's-algorithm topological sort: $O(V+E)$ time and space, no recursion so no stack-depth risk on large inputs.

💡 CONCEPT ANSWER

Subtracting a baseline doesn't change the expected gradient because $\mathbb{E}_{a\sim\pi_\theta(\cdot\mid s)}\big[\nabla_\theta\log\pi_\theta(a\mid s)\,b(s)\big] = b(s)\,\nabla_\theta\int_a \pi_\theta(a\mid s)\,da = b(s)\,\nabla_\theta(1) = 0$ for any $b$ that doesn't depend on the sampled action — so it's an unbiased correction term, not an approximation. It still helps because raw returns $G_t$ can have very different absolute scales and signs across episodes/states, so the estimator's variance is driven largely by *how far $G_t$ is from its typical value at that state*, not by the return itself. A well-chosen baseline (e.g. $V^\pi(s_t)$) recenters each term to (approximately) the advantage $A(s_t,a_t) = G_t - V^\pi(s_t)$, which is much smaller in magnitude and much more consistent across samples — same expected gradient direction, far less noise driving each individual update.
