# Day 90 — Concept 90: CLIP

## 🧠 CONCEPT OF THE DAY

**Intuition.** Yesterday's ViT turns an image into a single vector. Today's question: what if a *sentence* could land in that exact same vector space? CLIP (Contrastive Language-Image Pretraining) trains an image encoder and a text encoder side by side with one rule: the embedding of an image and the embedding of its correct caption should point in nearly the same direction, and the embedding of an image and any *wrong* caption should point in very different directions. No labels, no fixed class list — just ~400M scraped (image, caption) pairs off the internet, each pair pulling its two encoders' outputs together while every other caption in the batch pushes them apart. The payoff is startling: once trained, you can classify an image into *any* set of categories you dream up on the spot, just by writing each category as a sentence ("a photo of a {label}") and checking which sentence's embedding the image is closest to — zero task-specific training required.

**The math.** Given a batch of $N$ matched pairs $\{(I_i, T_i)\}_{i=1}^N$, an image encoder $f_I$ (a ViT, per yesterday, or a ResNet) and a text encoder $f_T$ (a standard Transformer, Day 60) each produce a vector, which is then L2-normalized onto the unit hypersphere:

$$v_i = \frac{f_I(I_i)}{\lVert f_I(I_i) \rVert_2}, \qquad u_i = \frac{f_T(T_i)}{\lVert f_T(T_i) \rVert_2}$$

Because both vectors have unit norm, their dot product *is* cosine similarity. Scale every pairwise similarity in the batch by a learned temperature $1/\tau$ to form an $N\times N$ logit matrix:

$$S_{ij} = \frac{v_i \cdot u_j}{\tau}$$

The diagonal $S_{ii}$ is the one true (image, caption) match; every off-diagonal entry in row $i$ is a "negative" — some other caption in the same batch, requiring zero explicit negative sampling. Training minimizes a **symmetric** cross-entropy (InfoNCE) loss, treating row $i$ of $S$ as image-$i$'s logits over which caption matches, and column $i$ as caption-$i$'s logits over which image matches:

$$\mathcal{L} = \frac12\left(-\frac1N\sum_i \log\frac{\exp(S_{ii})}{\sum_j \exp(S_{ij})} \;-\; \frac1N\sum_i \log\frac{\exp(S_{ii})}{\sum_j \exp(S_{ji})}\right)$$

Each term is exactly the softmax + cross-entropy machinery from Day 5, just applied over "which of these $N$ candidates is the match" instead of "which of these 10 classes is correct" — the entire batch doubles as the negative set.

**Why it matters / where it leads.** The shared embedding space is the real product, not the classifier — it's the exact mechanism behind zero-shot prompting (Day 70) applied to vision, and it's what feeds Stable Diffusion's cross-attention layers (Day 87): a CLIP text encoder's output *is* the conditioning signal a latent diffusion U-Net attends to when it turns "a photo of an astronaut riding a horse" into pixels. It also sets up tomorrow directly — SimCLR (Day 91) is the same InfoNCE machinery with both modalities replaced by a single image and its augmented copy, i.e. contrastive learning *without* needing paired text at all.

**Interview question:** *CLIP uses in-batch negatives instead of an explicit negative-sampling scheme — every other caption in the batch is automatically a negative for a given image. Why does this make batch size an unusually critical hyperparameter for CLIP specifically (more so than for a typical classifier), and what concretely goes wrong if you train it with a batch size of 32 instead of the ~32,768 the original paper used?*

## 🐍 PYTHONIC EDGE

The whole CLIP loss is "normalize two batches of vectors, multiply them together, run cross-entropy against the diagonal" — but the normalization and the temperature term are exactly where sloppy code introduces silent bugs (divide-by-zero, unbounded logits) that a few idiomatic calls avoid for free.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

# ---- BAD: manual L2 normalization, unclamped temperature ----
def clip_loss_bad(image_embeds, text_embeds, logit_scale):
    image_norms = image_embeds.pow(2).sum(dim=-1, keepdim=True).sqrt()  # dim=-1: last axis, regardless of rank -- no C++ equivalent shorthand
    text_norms = text_embeds.pow(2).sum(dim=-1, keepdim=True).sqrt()    # manual norm -- no epsilon guard, NaNs if a row is exactly zero
    image_embeds = image_embeds / image_norms
    text_embeds = text_embeds / text_norms
    logits = logit_scale * image_embeds @ text_embeds.t()              # @ is matmul (not bitwise-AND, unlike C++'s &); .t() transposes a 2D tensor
    labels = torch.arange(logits.shape[0])                             # torch.arange returns a real tensor object, not just a lazy range
    loss_i = F.cross_entropy(logits, labels)                           # rows: "which caption matches this image"
    loss_t = F.cross_entropy(logits.t(), labels)                       # cols: "which image matches this caption"
    return (loss_i + loss_t) / 2

# ---- CLEAN: F.normalize + a clamped, learned log-temperature ----
class CLIPLoss(nn.Module):                                              # class X(Base): single inheritance; C++: class X : public Base
    def __init__(self):
        super().__init__()                                              # runs nn.Module's __init__ first; C++ uses an initializer list instead
        init_value = torch.log(torch.tensor(1 / 0.07))                  # learned in LOG space so exp() can never go negative
        self.logit_scale = nn.Parameter(init_value)                     # instance attribute via self.x = ...; C++ declares in header, inits in body

    def forward(self, image_embeds, text_embeds):
        image_embeds = F.normalize(image_embeds, dim=-1)                # F.normalize folds the epsilon-guard + dim handling into one call
        text_embeds = F.normalize(text_embeds, dim=-1)
        logit_scale = self.logit_scale.exp().clamp(max=100)             # .clamp(max=...) caps runaway scale -- the fix for today's Signal Lab
        logits = logit_scale * image_embeds @ text_embeds.t()
        labels = torch.arange(logits.shape[0], device=logits.device)    # device=... kwarg keeps labels on the same GPU/CPU as logits
        return (F.cross_entropy(logits, labels) + F.cross_entropy(logits.t(), labels)) / 2

clip_loss = CLIPLoss()
img_embeds, txt_embeds = torch.randn(256, 512), torch.randn(256, 512)   # a batch of 256 matched (image, caption) embedding pairs
loss = clip_loss(img_embeds, txt_embeds)                                 # calls __call__, which wraps forward() with hooks -- never call .forward() directly
```

Both versions compute the same forward math, but `clip_loss_bad` will silently emit `NaN` the first time a degenerate zero-vector embedding shows up, and — as today's Signal Lab shows — an unclamped learned temperature is a live training-instability risk, not a hypothetical one; the original CLIP paper clamps it for exactly that reason.

## 📡 SIGNAL LAB

**Worked insight.** The right panel is the interesting one. Cosine similarity between embeddings is mathematically identical to a **matched filter's** correlation output between a signal and a template — the same "project onto a reference and read off the peak" operation from Nyquist-adjacent DSP work. Temperature scaling (`logit_scale`) then plays the role of a filter's *selectivity*: high scale is a narrow, high-Q correlator that turns a small similarity margin into near-certainty, exactly the way a narrowband filter converts a modest SNR into a sharp, confident detection peak. At low noise this is pure win — the green (`scale=100`) curve dominates. But push the noise up and watch the green curve, not just decline, but grow **jagged**: a high-Q filter's razor-sharp peak is also razor-sensitive to any perturbation that shifts which candidate ranks first, so as embedding noise starts occasionally flipping the true match's rank, a small ranking error gets amplified into a wildly different (and wildly wrong) softmax verdict. A flatter temperature (blue, `scale=1`) never gets that confident, but it also never gets *that* unstable.

**So what.** This is precisely why the clean code above wraps `logit_scale.exp()` in `.clamp(max=100)` instead of letting it train freely: `logit_scale` is a *learned* parameter, and nothing stops gradient descent from pushing it arbitrarily high to shave off a little more loss on the easy majority of pairs. Once it's high enough, the inevitable noisy or genuinely ambiguous (image, caption) pair in a real 400M-pair scrape produces the sharp-filter failure mode above: a single mis-ranked example generates a gradient spike large enough to destabilize the whole training run. The clamp is a hard-coded selectivity ceiling — the DSP equivalent of capping a filter's Q factor so a mismatched input can't blow up your correlator's output. For your own frequency-domain forensics work, the same tradeoff shows up any time you tune a detector's decision sharpness against real, imperfectly clean signal: more selective always looks better on your clean benchmark set, right up until it meets the noise your benchmark didn't have.

## 🏋️ THE GAUNTLET

**K Closest Points to Origin.** Given an array `points` where `points[i] = [xi, yi]` and an integer `k`, return the `k` closest points to the origin `(0, 0)` (in any order). "Closest" is measured by ordinary Euclidean distance.

**Constraints:**
- `1 <= k <= points.length <= 10^4`
- `-10^4 <= xi, yi <= 10^4`

**Hints (escalating):**
1. Sorting all `n` points by squared distance and taking the first `k` works in $O(n \log n)$ — but you don't actually need a *fully* sorted order, only the smallest `k`. When `k` is small relative to `n`, that's wasted work. What's the minimum structure that lets you track "the k smallest so far" without sorting everything?
2. A fixed-size **max-heap** of size `k` does exactly that: scan the points once, push each squared distance in, and whenever the heap exceeds size `k`, pop the *largest* — the same "keep only the top-k candidates seen so far, evict the worst" pattern you'd use to retrieve the k nearest neighbors to a CLIP query embedding out of a huge candidate pool. This gets you to $O(n \log k)$.
3. If you need average-case $O(n)$, use **quickselect**: partition the points around a pivot squared distance exactly like the partition step of quicksort, and recurse only into the side of the array that contains the `k`-th position — you never need to fully order either side.

**Pattern:** top-k selection via bounded max-heap ($O(n \log k)$) or quickselect ($O(n)$ average) — the same primitive behind picking the k nearest neighbors in any embedding-space retrieval problem. **Target complexity:** $O(n \log k)$ time / $O(k)$ space with the heap approach.

## 🔓 GAUNTLET SOLUTION

```cpp
#include <bits/stdc++.h>
using namespace std;

vector<vector<int>> kClosest(vector<vector<int>>& points, int k) {
    // max-heap on squared distance: the TOP of the heap is the farthest of our
    // current k candidates, so it's always the right one to evict.
    priority_queue<pair<long long, int>> maxHeap;   // (squared distance, index)

    for (int i = 0; i < (int)points.size(); ++i) {
        long long dist = (long long)points[i][0] * points[i][0]
                        + (long long)points[i][1] * points[i][1];
        maxHeap.push({dist, i});
        if ((int)maxHeap.size() > k) {
            maxHeap.pop();   // evict the current farthest candidate once we exceed k
        }
    }

    vector<vector<int>> result;
    result.reserve(k);
    while (!maxHeap.empty()) {
        result.push_back(points[maxHeap.top().second]);
        maxHeap.pop();
    }
    return result;
}
```

One pass building the heap ($O(n \log k)$, since each push/pop costs $O(\log k)$ against a heap capped at size `k`), then draining it ($O(k \log k)$). Overall $O(n \log k)$ time, $O(k)$ space — never materializes a full sorted order over all `n` points.

## 💡 CONCEPT ANSWER

Batch size matters unusually much for CLIP because the batch *is* the entire negative set — there's no separate negative-sampling mechanism to compensate for a small batch the way, say, a memory bank or momentum encoder can in other contrastive setups. With batch size 32, each anchor image only has to be distinguished from 31 other captions, most of which describe visually and semantically unrelated content — an easy discrimination task the model can solve while barely sharpening its embedding space at all, since "not a photo of a dog" is trivially separable from "a photo of a mountain" long before the representation is any good. The loss goes down, but the embedding space never gets pushed to make the *fine-grained* distinctions (this breed of dog vs. that one, this pose vs. a similar one) that zero-shot transfer actually depends on. At batch size ~32,768, every anchor is competing against tens of thousands of plausible near-miss captions, which forces the model to learn genuinely discriminative, well-separated structure across the whole space — that's the real training signal, and it only exists at scale. The systems-level trick that makes this affordable is **not** materializing the full $N\times N$ similarity matrix on a single device: real large-batch CLIP training shards the batch across many GPUs, computes local embeddings per-GPU, all-gathers just the embedding vectors (not the full similarity matrix) across devices, and each GPU then computes its own local rows of the loss against the full gathered set — giving you a huge *effective* batch size without any single device ever holding an $O(N^2)$ tensor in memory.
