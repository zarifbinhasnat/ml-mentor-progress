# Day 95 — Object Detection: Anchors, IoU, NMS, YOLO

## 🧠 CONCEPT OF THE DAY

**Intuition.** Classification answers "what is in this image?" Detection answers "what is in this image, and *where*, for every instance, simultaneously." The trick that makes this tractable is to stop asking the network to invent boxes from scratch and instead give it a dense grid of **candidate boxes (anchors)** — fixed-size, fixed-position rectangles tiled over the feature map — and ask two much easier questions per anchor: *"is there an object here, and if so, nudge me toward its true box and tell me its class."* Regression from a good starting guess (the anchor) is far easier to learn than regression from nothing.

That dense tiling creates a new problem: dozens of anchors will fire on the same object, all claiming "car, 92% confident" with slightly different boxes. **IoU (Intersection over Union)** is the metric that lets you say two boxes are "the same detection," and **NMS (Non-Max Suppression)** is the greedy algorithm that collapses a cloud of redundant boxes down to one per object.

**The math.**

IoU between boxes $A$ and $B$:

$$\text{IoU}(A, B) = \frac{|A \cap B|}{|A \cup B|}$$

where $|A \cap B|$ is the overlap area and $|A \cup B| = |A| + |B| - |A \cap B|$. IoU is 0 for disjoint boxes, 1 for identical boxes — it's the standard "how well do these two boxes agree" score used both for NMS *and* for grading a detector against ground truth (a prediction counts as a match if $\text{IoU} \geq 0.5$, the classic mAP@0.5 threshold).

YOLO-style anchor decoding — the network doesn't predict raw pixel coordinates, it predicts small offsets from a grid cell $(c_x, c_y)$ and an anchor's prior width/height $(p_w, p_h)$:

$$b_x = \sigma(t_x) + c_x, \quad b_y = \sigma(t_y) + c_y, \quad b_w = p_w e^{t_w}, \quad b_h = p_h e^{t_h}$$

$\sigma(\cdot)$ (sigmoid) keeps the center offset inside its own grid cell; $e^{t_w}, e^{t_h}$ let width/height scale the anchor prior up or down multiplicatively and can never go negative. $(t_x, t_y, t_w, t_h)$ are the network's raw outputs — everything else is a fixed geometric prior.

Greedy NMS, per class:

$$\text{repeat: pick the highest-scoring remaining box } b^*, \text{ discard every box } b \text{ with } \text{IoU}(b^*, b) > \tau$$

until no boxes remain. $\tau$ (typically 0.45–0.5) is a knob: too low and you delete legitimately separate, tightly-packed objects; too high and duplicate boxes survive.

**Why it matters.** This is the last stop before Phase 10 (efficient serving), and detection is where inference-time cost stops being "just FLOPs" — NMS is a sequential, data-dependent, variable-length loop that doesn't batch cleanly on a GPU, which is exactly the kind of serving headache Phase 10 exists to address. It's also a *very* live interview topic because the failure mode is subtle and testable.

**Interview question:** *You're running NMS with IoU threshold 0.5 on a security-camera feed of a dense crowd, and two genuinely distinct people standing close together keep collapsing into one detection. Why does standard NMS do this, and what's one concrete fix?*

## 🐍 PYTHONIC EDGE

Computing IoU between one box and *many* boxes is the operation you'll write a thousand times. The naive version loops in Python; the idiomatic version broadcasts.

```python
import numpy as np

# ---- the bad way: Python-level loop, O(n) Python overhead per call ----
def iou_loop(box, others):
    ious = []
    for other in others:                 # each iteration pays full Python interpreter overhead
        x1 = max(box[0], other[0])
        y1 = max(box[1], other[1])
        x2 = min(box[2], other[2])
        y2 = min(box[3], other[3])
        inter = max(0, x2 - x1) * max(0, y2 - y1)
        area_b = (box[2] - box[0]) * (box[3] - box[1])
        area_o = (other[2] - other[0]) * (other[3] - other[1])
        ious.append(inter / (area_b + area_o - inter))
    return ious                            # returns a plain list, not an array

# ---- the clean way: vectorized, the loop runs in compiled C, not Python ----
def iou_vec(box, others):
    # others: shape (N, 5) — [x1, y1, x2, y2, score]. box: shape (5,)
    x1 = np.maximum(box[0], others[:, 0])   # np.maximum is elementwise; Python's max() is not
    y1 = np.maximum(box[1], others[:, 1])
    x2 = np.minimum(box[2], others[:, 2])
    y2 = np.minimum(box[3], others[:, 3])

    inter_w = np.clip(x2 - x1, 0, None)     # None as an upper bound means "no cap" — clamps only the low side
    inter_h = np.clip(y2 - y1, 0, None)
    inter = inter_w * inter_h               # elementwise multiply, NOT matrix multiply (that would be @)

    area_box = (box[2] - box[0]) * (box[3] - box[1])
    area_others = (others[:, 2] - others[:, 0]) * (others[:, 3] - others[:, 1])
    return inter / (area_box + area_others - inter)   # returns shape (N,) array, no Python-level loop at all
```

`others[:, 0]` is NumPy slice notation — `:` means "every row," `0` means "column 0" (Python's `list[a:b]` slicing generalizes to a comma-separated tuple of slices/indices per axis; C++ has no built-in equivalent, you'd hand-write index arithmetic). `others[:, 2] - others[:, 0]` subtracts two full column-vectors elementwise in one call — no loop, no `.at()`, no bounds-checked indexing overhead.

## 📡 SIGNAL LAB

NMS is a spatial-domain instance of a pattern you already know from spectral analysis: **greedy local-maximum suppression**. When you find dominant frequencies in a PSD (power spectral density), you don't report every bin above a noise floor — nearby bins around a true peak are just spectral leakage of the *same* underlying sinusoid, so you pick the tallest bin in a neighborhood and suppress everything within some minimum frequency separation around it. That's NMS with 1D "boxes" (frequency bins) and "IoU" replaced by "distance under a minimum-separation threshold."

**Worked example.** Two sinusoids at 50 Hz and 53 Hz, sampled at $f_s = 500\text{ Hz}$ for $N = 128$ samples ($\approx 0.256\text{ s}$). Frequency resolution of a plain DFT is $\Delta f = f_s / N \approx 3.9\text{ Hz}$ — right at the edge of resolving two peaks only 3 Hz apart, so the DFT magnitude spectrum shows a *single broadened lobe*, not two separate peaks (this is spectral leakage / limited resolution, not noise). Naive "take every local max above threshold" would report one peak; a longer window ($N = 1024 \Rightarrow \Delta f \approx 0.49\text{ Hz}$) resolves them into two distinct, suppressible peaks.

**So what:** just as NMS's IoU threshold $\tau$ trades off "merge near-duplicates" against "wrongly merge two real, close objects," your peak-picking minimum-separation trades off "reject spectral leakage as one peak" against "wrongly merge two real, closely-spaced frequency components." In both domains the fix for *false merges* is the same lever: increase resolution (longer window in frequency; higher-resolution feature map / more anchor scales in detection) — you can't fix an under-resolved input with a smarter suppression rule alone.

## 🏋️ THE GAUNTLET

**Problem: Max Compatible Jobs**

You're given $n$ candidate detections on a single scanline, each as $(\text{start}_i, \text{end}_i, \text{score}_i)$ — think of them as 1D intervals with a confidence score. You want to select the **maximum number** of intervals such that no two selected intervals overlap (share any point). Scores are given but, for this version of the problem, ignored — you're maximizing *count*, not summed score.

**Constraints:** $1 \le n \le 2 \times 10^5$, $0 \le \text{start}_i < \text{end}_i \le 10^9$.

**Hints (escalating):**
1. This is not a DP-over-all-subsets problem — $n$ is too large, and there's a greedy exchange argument lurking. Think about what property of an interval makes it "safe" to commit to immediately, before you've even looked at the rest.
2. Sorting by start time is the intuitive first move and it's a trap for this objective — construct a small counterexample where sorting by start time picks fewer intervals than optimal. What single sort key never loses to the optimal solution?
3. Once sorted by the right key, the rest is one linear pass with one running variable (the end time of your last accepted interval) — no data structure needed beyond the sort itself.

**Pattern:** Greedy interval scheduling (activity selection). **Target complexity:** $O(n \log n)$.

## 🏗️ BLUEPRINT

**Anchor-based detectors (Faster R-CNN, YOLO) vs. anchor-free/set-based detectors (DETR) is fundamentally a "who owns the deduplication cost" tradeoff.** Anchor-based models are fast and mature but ship NMS as a mandatory, sequential, data-dependent post-processing step — it runs on CPU or in an awkward GPU kernel, its latency depends on *how many objects are in the scene* (not a fixed FLOP count), and it's a genuine pain to export cleanly to ONNX/TensorRT. DETR reframes detection as direct set prediction (Hungarian matching at train time, fixed $N$ output queries at inference) and needs **no NMS at all** — inference cost is fixed and batches perfectly — but pays for it with far slower convergence (originally 500 epochs vs. YOLO's ~300) and weaker small-object performance from the sparse query set. When you're choosing an architecture for a **latency-SLA'd real-time system** (autonomous driving, live video), "no NMS" isn't a nicety — it's often the deciding factor, because a data-dependent tail latency spike from a crowded frame is worse than a slightly lower mAP.

🔓 GAUNTLET SOLUTION

```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    cin >> n;
    vector<pair<long long, long long>> iv(n); // (end, start) — sort key is end time
    for (int i = 0; i < n; i++) {
        long long s, e, score;
        cin >> s >> e >> score;   // score read but unused in this variant
        iv[i] = {e, s};
    }

    sort(iv.begin(), iv.end());   // sort ascending by end time

    int count = 0;
    long long last_end = LLONG_MIN;
    for (auto &[e, s] : iv) {
        if (s >= last_end) {      // safe to take: doesn't overlap the last accepted interval
            count++;
            last_end = e;
        }
    }

    cout << count << "\n";
    return 0;
}
```

Why "sort by end time" beats "sort by start time": greedily committing to the interval that finishes *earliest* leaves the maximum possible room for everything after it — this is the same exchange argument behind classroom/activity scheduling. Sorting by start time can lock in a long interval early and block out several short ones that would've fit; sorting by end time never does, because whatever interval the optimal solution picks first, swapping it for the earliest-finishing compatible interval can only free up more room, never less.

💡 CONCEPT ANSWER

Standard NMS suppresses *any* box whose IoU with the top-scoring box exceeds $\tau$, using **only geometric overlap** — it has no notion of "these are two different objects that happen to be close" versus "these are duplicate detections of one object." In a dense crowd, two real people standing shoulder-to-shoulder produce boxes with genuinely high mutual IoU, so the lower-scoring correct detection gets discarded exactly like a redundant duplicate would. One concrete fix: **Soft-NMS** — instead of hard-discarding overlapping boxes, decay their scores continuously as a function of IoU (e.g. $s_i \leftarrow s_i \cdot e^{-\text{IoU}(b^*, b_i)^2/\sigma}$) and only drop boxes once their score falls below a separate confidence threshold. This keeps the second person's detection alive (lower score, but not zero) unless the overlap is extreme, trading a small amount of duplicate-suppression aggressiveness for much better recall in crowded scenes.
